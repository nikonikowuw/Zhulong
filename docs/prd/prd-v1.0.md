## 2. 产品概述

### 2.1 产品定位

Zhulong 是面向本地部署的深度学习 NVR / 边缘视频分析系统。产品目标是接入网络摄像机或视频流，在设备侧管理采集与分析任务，基于可配置规则生成抓拍、告警和识别记录，并通过 Web 控制台完成设备、任务和证据运维。

Zhulong 以单台设备自主运行和可维护为目标。具体部署操作系统、设备型号、媒体协议、模型运行时和多设备管理方式尚未最终确定。

### 2.2 用户与主要场景

| 用户 | 主要场景 |
| --- | --- |
| 现场管理员 | 首次初始化系统、维护管理员凭据、添加摄像机、检查设备状态和审计操作。 |
| 值班人员 | 查看实时画面和告警，检索抓拍及识别结果，查看事件图像并进行业务核验。 |
| 集成与算法开发人员 | 评估目标平台、集成算法能力、配置分析任务，并验证模型精度、资源占用和稳定性。 |

### 2.3 产品目标

- 提供从摄像机接入、分析任务配置到事件证据查询的端侧工作流。
- 支持按摄像机配置实时预览和分析任务，并控制任务的启停与资源释放。
- 支持目标检测结果上的区域、越线、过滤等空间规则及事件抑制能力。
- 提供抓拍、告警、识别三类可检索的证据工作流，并保护重要证据不被普通清理流程优先删除。
- 通过本地 Web 控制台管理设备、任务、规则、算法能力、用户操作审计和证据。
- 明确记录哪些能力已实现、哪些为规划需求、哪些依赖尚待选择的硬件或软件方案。

### 2.4 非目标

- 本版本不定义云端集中管理、跨站点租户体系或企业级多级 RBAC 的交付承诺。
- 不在本 PRD 中选择具体 NPU、摄像机品牌 SDK、解码 SDK、模型格式或推理供应商。
- 不要求全静态链接、零宿主动态依赖或完全无需系统/厂商运行时。
- 不定义算法库进程内加载即构成安全沙箱；包校验、自测和代码隔离是不同的安全能力。

## 3. 已确认架构与技术边界

### 3.1 系统拓扑

```text
React Web SPA
  React 18+, TypeScript strict, Vite, React Router
  TanStack Query, Tailwind CSS + shadcn/ui
  深色/浅色主题；英文、简体中文、繁体中文
        │ HTTP (Gin) / SSE (推理事件) / WebSocket (设备遥测)
        ▼
Go 应用宿主
  Gin、Fx、GORM + SQLite、Swaggo / Swagger 2.0、Uber Zap
  内嵌 Vite 静态资源；管理业务、配置、生命周期与持久化

        ▼
C++ 视频处理 Pipeline
  采集 → 解码 → 预处理 → 推理及结果处理
        │ 平台适配层 / 系统接口
        ▼
摄像机、编解码设备、图像处理器、NPU/GPU 与厂商运行时
```

### 3.2 已确认项目约束

- **单宿主交付：** Go 作为单一应用宿主；React 静态构建产物通过 Go `//go:embed` 内嵌并由宿主托管。该约束不等同于全静态二进制。
- **Go 后端：** Gin 处理 HTTP，Fx 管理依赖装配与应用生命周期，GORM 访问 SQLite，Swaggo 生成 Swagger 2.0 API 文档，Uber Zap 提供结构化日志。
- **原生引擎：** 视频处理 Pipeline 使用 C++。Go 通过 CGO 调用稳定 C ABI；不得把 C++ 类、模板、异常或标准库类型暴露为跨语言接口。
- **前端：** React 18 或更新版本、严格 TypeScript、Vite、React Router、TanStack Query、Zustand（仅必要的纯 UI 状态）、React Hook Form + Zod、Tailwind CSS + shadcn/ui、Vitest + React Testing Library。
- **数据目录：** SQLite 数据、录像、证据、模型和其他可写资产放在可配置的外部数据目录，不假定它们能写入嵌入式前端资源或应用二进制。
- **外部依赖：** 允许目标系统的 C 运行时、线程库、编解码库和厂商硬件运行时等已文档化的依赖；具体部署清单须按目标平台验证。
- **HTTP 响应：** JSON API 使用必需的 `{ "code": "...", "message": "...", "data": ... }` 响应信封；HTTP 422 字段校验失败时可附加顶层 `details` 数组。错误响应的 `data` 必须为 `null`。`details` 每项包含稳定字段路径、错误码和按 `Accept-Language` 本地化的消息；不得包含原始输入。内部数据库、驱动和 CGO 错误不得原样返回客户端。

## 4. 功能需求

### 4.1 初始化、身份认证与审计

#### 4.1.1 首次初始化与管理员访问

- 系统应能识别是否完成首次初始化；未初始化时引导管理员设置凭据后再进入正常管理流程。
- 系统不得依赖公开的固定默认密码。密码复杂度、哈希算法、认证会话/令牌时限和暴力尝试限制须在安全设计中确定。
- 自动化初始化环境变量、恢复密码 CLI 命令、配置文件格式和具体字段名均为待决项。若采用产品专属环境变量，应使用 `Zhulong_` 命名空间；不得沿用其他产品名称。
- 管理员凭据恢复应避免通过删除数据库来重置，具体的受控恢复流程需另行设计和验证。

#### 4.1.2 操作审计

- 系统应记录关键管理写操作，包括操作主体、时间、来源地址、请求路径、结果状态和耗时。
- 审计内容不得持久化明文密码、令牌或其他敏感凭据；请求体如需记录，必须先按字段策略脱敏。
- 控制台应提供按时间和业务模块筛选审计记录的能力。
- 审计中间件、审计存储和异步落盘策略属于实现设计；不得阻塞关键数据一致性或泄露内部错误。

### 4.2 摄像机与媒体接入

- 管理员应能添加、编辑、删除和探测摄像机/视频源，并查看连接状态、最近探测结果和可用流信息。
- 产品应支持为同一摄像机配置适合预览与分析的一个或多个媒体流；主/子码流选择和缺少子码流时的回退行为应在界面明确呈现。
- 多个预览或分析订阅共享视频源、按需启动连接、在无订阅时释放资源是产品目标；连接复用键、空闲冷却时间和重连退避尚待设计。
- RTSP、ONVIF、特定品牌 URL 推导、认证方式、RTP over TCP/UDP、支持的 codec/container 与相机型号清单均须由兼容性测试确认，不视为当前已支持。
- 系统应向操作员呈现断流、认证失败、配置错误和资源不可用等可诊断状态；重试策略须有超时和上限，避免无限快速重连。

### 4.3 实时预览与媒体传输

- 控制台应提供实时预览，并在允许的设备能力下支持多个画面布局和主/子流切换。
- 系统应以端到端播放延迟、浏览器/编解码兼容性、部署复杂度和设备资源占用评估实时传输方案。
- HTTP-FLV、WebSocket-FLV、Enhanced FLV、MSE、WebRTC/WHEP 等均为候选技术，不是当前已经批准的媒体合同。协议、端点、播放器库、H.264/H.265 支持范围和鉴权方式待专项决策。
- 规则编辑器可在已选定的实时画面上叠加交互绘制层；若目标平台或浏览器无法稳定提供实时画面，系统须提供明确错误/降级状态，不得静默保存错误坐标。

### 4.4 分析任务与算法能力

#### 4.4.1 分析任务

- 用户应能创建、查看、修改、启用和停止分析任务，并将摄像机、算法能力、输入流与规则关联。
- 任务状态应区分期望状态与实际运行状态，并展示启动失败、输入断流、算法不可用等原因。
- Pipeline 的采集、解码、预处理和推理节点应遵循有界队列与明确背压策略；推理拥塞不能导致无界内存增长。录像完整性与实时推理新鲜度的丢帧策略应分别定义。
- 任务关闭或应用退出时，应停止新输入、取消/唤醒阻塞队列、等待工作线程退出，再释放解码器、推理上下文和缓冲区等资源。

#### 4.4.2 算法包管理

- 产品应提供算法能力的登记、兼容性信息展示、自检结果查看、启停和可追踪版本管理。
- 包上传、manifest/schema 校验、哈希/签名校验、真实输入自测和安装回滚是待设计的候选流程；校验步骤不得被描述为对不可信原生代码的安全隔离。
- 算法包目录格式、ABI 名称/版本、动态装载、热更新、平台标签和配置 schema 均须与目标 SDK、C ABI 及威胁模型共同评审后定义。
- 支持目标检测、人脸和车牌等感知能力属于产品范围；具体模型、推理后端、类别标签、精度、特征维度与阈值均未选定。

### 4.5 规则、跟踪与事件

- 系统应支持按业务需要配置目标区域过滤/入侵、越线、方向或其他空间规则，并可在规则编辑时校验范围、点数和坐标。
- 规则坐标应能映射到实际视频帧；前端画面比例、旋转、裁剪和流切换不得造成保存与运行坐标不一致。
- 系统应能关联连续检测结果以生成目标轨迹，并支持基于事件/目标的重复抑制和冷却。
- ROI、Mask、Line、目标底部中心判定、方向约定、ByteTrack、预裁剪 ROI 和固定冷却时长均为候选细节，应通过算法验证和产品验收确定。
- 实时画面应避免不必要的高频叠加信息；有事件时应能将操作员引导到相关摄像机、规则和证据记录。

### 4.6 抓拍、告警与高清证据

- 当分析结果满足业务规则时，系统应创建关联摄像机、任务、规则、时间、目标属性和图像资源的告警记录。
- 系统应支持正常目标的抓拍/行迹回溯以及事件触发的告警证据；当产品启用识别能力时，还应记录识别输入、匹配结果与核验状态。
- 目标特写图、全景图和主/子流证据关联属于产品需求。双流采集、压缩码流环形缓存、按 PTS 回溯解码、零拷贝及 JPEG 编码器是候选实现，须验证时间同步、内存占用和断流降级。
- 主流证据无法取得时，产品应按明确策略降级、重试或报告证据缺失；不得承诺所有情况下均百分之百生成高清图。
- 图像元数据应能关联相机、任务、目标/轨迹和事件，并可按权限受控访问。

### 4.7 识别与底库

- 产品目标包括人脸或车牌等对象的识别记录、候选底库登记和 1:N 匹配核验工作流。
- 识别记录应区分“未匹配”“候选命中”和“人工确认”等状态，避免把模型分数直接呈现为确定身份。
- 特征向量格式、精度、维度、距离度量、阈值、索引方式和内存驻留策略均须待模型与硬件选型后确定。
- 人脸、车牌及身份信息属于敏感数据。采集授权、访问控制、加密、留存期限、删除和导出流程必须在上线前经安全与合规审查确认。

### 4.8 存储、保留与一致性

- 数据库、录像、模型、配置和证据文件应位于可配置且可写的数据目录；容量配额、保留期限和磁盘低水位须允许运维配置或通过受控默认值管理。
- 存储保护应按业务价值优先保留告警等关键证据，可优先清理低价值或到期内容；具体优先级、批次和默认水位须评审确认。
- 文件系统与 SQLite 不支持由单个普通数据库事务保证共同原子提交。清理流程必须可恢复、幂等，并提供孤儿文件/缺失文件检测或修复策略；不可承诺简单 `unlink` 与 SQL `DELETE` 原子联动。
- SQLite schema 变更必须使用有序、版本化迁移，由应用启动时在对外提供 API 或启动 Pipeline 前执行。迁移失败时应阻止服务进入就绪状态，并保留用户数据。
- GORM `AutoMigrate` 不得替代版本化升级路径。实体关系、索引、物理列类型、级联删除和 WAL 参数由后续数据设计确定。

### 4.9 Web 控制台

- 控制台应覆盖初始化/登录、实时预览、摄像机管理、任务管理、规则编辑、算法能力管理、告警、抓拍、识别/底库和操作审计等核心工作流。
- 实时视图可提供 1/4/9 等多画面布局作为产品候选；最终并发上限须按浏览器和设备基线验证。
- 证据中心应分别支持告警处置、抓拍检索与识别核验；图像详情应显示其来源、时间和关联记录。
- 前端应对每个异步操作提供 loading、error 和 empty 状态；错误 Toast 直接展示后端按语言返回的 `message`。
- React 组件使用函数组件与 Hooks；组件保持单一 UI 职责，数据请求和复杂业务逻辑抽取到 Hooks；不以机械行数拆分组件。
- TanStack Query 管理服务端数据；Zustand 仅用于确有需要的跨组件 UI 状态。禁止将服务端数据复制到全局客户端 store。
- 组件 Props 必须显式定义类型；禁止 `any`；稳定列表 key 不使用数组索引。优先语义化 HTML 和键盘可操作交互；只在有 Profiler 证据时采用 `memo`、`useMemo`、`useCallback`。
- 浅色与深色主题必须覆盖页面、组件、表单、对话框、弹层、图表和交互状态。
- 所有用户可见文本须完整支持英文（`en`）、简体中文（`zh-Hans`）和繁体中文（`zh-Hant`），包括按钮、校验错误、Toast、tooltip、图表、空/错/加载状态和无障碍名称。
- 首次访问时主题跟随系统、语言跟随浏览器偏好，未支持的语言回退英文；用户显式选择应持久化并优先于后续系统偏好变化。
- 跨功能共享代码放在 `src/shared`；功能模块按 `src/features/<module>/...` 组织；跨模块只通过所属功能的 `index.ts` 公共出口导入，并使用 `@/` 路径别名，避免多层相对路径。

## 5. API 与数据需求

### 5.1 HTTP 响应和错误

所有 JSON 响应必须包含 `code`、`message`、`data` 三个字段；只有 HTTP 422 字段校验错误可以额外包含 `details`。错误响应的 `data` 固定为 `null`。

成功响应示例：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "id": "camera-01",
    "name": "Gate 1"
  }
}
```

一般错误响应示例：

```json
{
  "code": "CAMERA_NOT_FOUND",
  "message": "Camera not found",
  "data": null
}
```

字段校验错误示例：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "data": null,
  "details": [
    {
      "field": "name",
      "code": "REQUIRED",
      "message": "Name is required"
    }
  ]
}
```

- `code` 使用稳定的机器可读字符串；成功码为 `OK`，错误码使用大写蛇形命名。
- `details` 仅用于 HTTP 422 字段校验错误。每项包含请求 JSON 字段路径、稳定字段错误码和用户可读消息；不得包含被拒绝的原始字段值。
- `message` 及 `details[].message` 均按 `Accept-Language` 本地化。其他错误不返回 `details`。
- HTTP 状态码须表达成功、客户端错误和服务端错误语义；不得只依赖响应体中的业务码。
- 内部错误详情通过 Zap 结构化日志记录并脱敏，不返回堆栈、CGO 或数据库原始错误。
- 字段命名和时间/时区序列化策略需在 API 规范中统一；不在本 PRD 中预设冗余时间戳字段或不一致的格式。
- Swaggo 生成的 Swagger 2.0 文档应与已实现 API、认证方式、请求校验、响应信封和错误状态保持同步。

## 6. 非功能需求与候选指标

下表数值来自需求探索，尚无 Zhulong 靶机或实现测量结果。它们是待讨论的候选基线，不是当前 SLA 或已达成性能。确认前必须定义设备型号、系统/驱动/SDK 版本、codec、模型与量化类型、温度/功耗模式、并发路数和测量起止点。

| 指标 | 候选目标 | 必须补充的验证条件 |
| --- | --- | --- |
| 实时预览端到端延迟 | 局域网内不高于 400 ms；200–300 ms 仅为探索目标 | 摄像机到浏览器呈现的完整路径、协议、浏览器、分辨率和 codec。 |
| 单帧推理耗时 | 640×360 输入不高于 15 ms | 指定模型/量化类型、预处理和后处理是否计时、NPU/GPU/CPU 运行后端。 |
| 规则触发到界面事件 | 不高于 100 ms | 事件产生、Go 接收、网络发送到浏览器显示的边界与并发负载。 |
| 空闲内存 | 不高于 45 MB | 目标系统、进程测量口径、运行时已加载状态。 |
| 多路分析资源 | 4 路 1080P/4K 输入场景下内存不高于 200 MB、CPU 不高于 12% | 子流推理/主流证据策略、硬件加速状态、预览数及系统统计口径。 |
| 存储保护 | 低水位候选为可用空间 15% | 文件系统、配额、保留策略、突发写入量及清理可恢复性。 |

正式验收指标须经过原型测量和所有者评审；任何平台/模型更换都需重新确认基线。精度要求、误报漏报、长时间稳定性、启动时长、断流恢复和关机清理能力也需在具体功能验收中补充。

## 7. 命名与可维护性要求

- 文件名、命令、参数、函数/方法及变量名应准确表达领域含义、自然易读，避免为追求短小而引入含糊缩写。
- 分别遵循 Go、C++、TypeScript 的惯用命名规则；跨语言共享领域词汇，但不强制不同语言采用相同大小写形式。
- 面向用户的可执行程序或配置前缀可使用 `Zhulong` / `Zhulong_`；具体命令、flag 和环境变量名称在其公开接口定稿前仅作建议，不得伪装成已实现接口。
- API 字段、数据库内部字段、C ABI 符号和 UI 文案应在各自边界保持一致、稳定，并避免暴露内部实现细节。

## 8. 实施路线建议

以下是能力依赖顺序建议，不代表已承诺的项目排期或阶段完成状态：

1. **应用骨架与边界：** 建立 Go 宿主、Gin API、Fx 生命周期、GORM/SQLite 版本化迁移、Zap 日志、Swagger 生成和 React 内嵌交付；设计最小 C ABI 与 C++ Pipeline 生命周期。
2. **媒体输入与运维：** 选择目标平台和媒体方案，完成摄像机配置/探测、连接恢复、实时预览及设备状态可观测性。
3. **分析和证据链路：** 验证模型/SDK/量化与算法集成方案，再实现任务调度、规则、事件、抓拍/告警、识别及可靠存储管理。
4. **控制台闭环与平台验收：** 完成实时规则工作台、证据中心、审计和多语言/主题矩阵测试；在选定靶机上验证精度、性能、长稳、故障恢复与发布依赖。

Apple Silicon、Rockchip、Huawei Ascend 等平台可作为评估候选；在正式选择并验证 SDK、驱动、模型转换和部署约束前，不承诺同时支持或声明兼容。

## 9. 待决事项与验收准备

进入对应实现或采购阶段前，至少需要确认：

- 首发操作系统、CPU 架构、目标板卡、内核/BSP、交付方式与外部运行时清单。
- 摄像机兼容范围、媒体协议、编解码和浏览器播放技术，以及实时预览鉴权方式。
- Pipeline 调度/缓冲策略、C ABI 版本与生命周期合同、目标 SDK 和模型/量化方案。
- 算法包信任来源、签名、更新/回滚策略及真实隔离威胁模型。
- 管理员恢复、凭据存储、角色模型、识别数据授权/保留/删除策略。
- 数据迁移、录像与证据文件格式、存储水位和候选性能/精度指标的可重复测试方法。

每项验收应分别标明“产品行为通过”“指定平台验证通过”或“仍待选/待测”。无应用源码或测试包时，只能报告文档校验结果，不能报告应用功能或性能通过。
