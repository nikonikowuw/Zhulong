# Zhulong 跨语言命名规范

> 适用于 Go、C/C++、TypeScript/React 源码，及文件名、CLI 命令和参数。本文是项目级命名规则的单一来源；各语言保持自身惯例，不强行统一大小写。

## 1. 命名目标

1. **自然、见名知意优先**：名称要让读者不跳转定义也能理解其业务含义或职责。
2. **清晰优先于短小**：名称长一些没有问题；不要为少打几个字符而截断单词、制造缩写或丢失语义。
3. **使用稳定的领域词汇**：同一业务概念在 API、日志、前后端和原生边界尽量使用同一术语；确有差异时在对应契约中说明。
4. **避免重复和空泛**：名称应补充上下文，而不是重复包名、目录名或类型信息。避免脱离上下文仍无法辨认的 `data`、`info`、`util`、`manager`、`process` 等泛称；只有在局部作用域含义明确时才使用。
5. **缩写有边界**：只使用团队和目标读者普遍理解的缩写，如 `ID`、`URL`、`HTTP`、`RTSP`、`NPU`。新领域缩写首次出现时给出全称；不要创造仅为缩短名称服务的缩写。
6. **名称不编码易变实现细节**：表达稳定职责和业务意图，不因当前算法、底层库或临时实现方式给长期接口命名。

## 2. 文件与目录

- 文件名说明领域对象或职责；需要区分同目录中的多个职责时可使用更完整的名称，不追求最短。
- 避免 `misc`、`tmp`、`stuff`、无明确边界的 `common` 或 `utils`。已有架构目录能表达领域时，不重复添加多余前缀。
- Go 文件使用小写单词和下划线，并保留 `_test.go`、操作系统及架构后缀等工具链约定。
- C/C++ 源文件与头文件使用小写下划线命名，配对文件保持相同主干名。
- React 组件文件使用与主要导出组件一致的 `PascalCase.tsx`；Hook 文件以 `use` 开头并与 Hook 名称一致；其他 TypeScript 模块使用 `camelCase.ts`。既有 `index.ts`、`types.ts` 等目录门面文件按目录规范保留。

| 不推荐 | 推荐 | 原因 |
| --- | --- | --- |
| `misc.go` | `recording_retention.go` | 表明所属职责 |
| `f1.cpp` | `rtsp_source.cpp` | 可从文件名识别组件角色 |
| `Panel.tsx` | `CameraStatusPanel.tsx` | 明确页面对象和视图职责 |

## 3. CLI 命令与参数

- 命令及参数使用小写 `kebab-case`；命令按领域分组，子命令使用清晰的动作词，并在同一组中保持语法一致。
- 参数名称描述完整含义；涉及单位且单位可能产生歧义时，在名称或帮助文本中明确单位。
- 除普遍约定的短选项外，不用难以猜测的缩写；短别名不能代替帮助文本中的完整名称。

```text
# 不推荐：含义依赖猜测
Zhulong cam ls -u

# 推荐：领域、动作和参数都明确
Zhulong camera list
Zhulong camera add --rtsp-url <url>
```

以上命令仅示范命名方式，不代表已实现的 Zhulong CLI 接口。

## 4. 按语言遵循惯例

| 语言 | 类型 / 导出符号 | 函数与变量 | 文件名 / 补充规则 |
| --- | --- | --- | --- |
| Go | 导出标识符使用 `MixedCaps`，非导出使用 `mixedCaps`；标准初始缩写保持一致，如 `ID`、`URL`、`HTTP` | 使用表达意图的动词或领域名词；接收者名称简洁但可辨认；包名使用简短、小写、无下划线的领域词 | 小写单词加下划线；文件名不重复包名已充分表达的上下文 |
| C/C++ | 类型使用 `PascalCase`；C ABI 符号按 ABI 规范使用项目名前缀和小写下划线 | 函数、局部变量和成员按 `lower_snake_case`；宏使用项目名前缀和大写下划线，并尽量避免新增宏 | 小写下划线；配对的头文件和源文件保持相同主干名 |
| TypeScript / React | 组件、类型和接口使用 `PascalCase`；不加冗余的 `I` 前缀 | 函数、变量和属性使用 `camelCase`；Hook 使用 `use` 前缀 | 组件文件匹配组件名；Hook 文件匹配 Hook 名；其他模块使用 `camelCase` |

同一概念在不同语言中可以采用不同大小写，例如 Go `cameraID`、C++ `camera_id`、TypeScript `cameraId`；语义应保持一致。序列化字段按对应 API 契约命名，不要求与语言内标识符大小写相同。

## 5. 函数、变量与参数

- 函数和方法使用能说明动作及对象的名称；区分读取、创建、更新、删除、校验等行为，避免没有上下文的 `do`、`handle`、`process`。
- 变量描述其代表的领域对象、状态或用途。集合使用可识别复数形式；映射应说明键和值的关系，如 `cameraByID`。
- 布尔值优先使用正向、可直接判断的名称，如 `isReady`、`hasCapacity`；避免双重否定。
- 当数值单位、时区、坐标系或生命周期会影响正确性时，将其表达在名称或紧邻的类型/文档中。
- 缩写只在约定俗成且作用域足够清楚时使用。窄作用域中的常规循环索引等惯用短名可以保留；不把这种例外扩展到公共 API、跨模块契约或长生命周期状态。

| 语言 | 不推荐 | 推荐 |
| --- | --- | --- |
| Go | `findCam(c string)` | `findCameraByID(cameraID string)` |
| C++ | `void proc(Frame& f)` | `void decodeVideoFrame(const EncodedVideoPacket& encoded_packet)` |
| TypeScript | `const d = camera.retention` | `const recordingRetentionDuration = camera.recordingRetentionDuration` |

推荐名称并非越长越好：只要现有词语已清楚表达职责，就不要添加重复信息；当更完整的名称能减少猜测时，优先保留完整表达。

## 6. 评审检查

新增或重命名文件、命令、函数、变量及跨层字段时，检查：

- 名称是否自然，能否直接看出业务概念或职责？
- 是否存在更明确但不冗余的完整词语？
- 同一概念在 Go、C/C++、TypeScript 和跨层契约中是否使用一致术语？
- 命名格式是否符合所属语言和目录的既定惯例？
- 缩写是否为读者熟悉且稳定的术语？

命名语义主要通过代码评审判断，不为此引入只检查长度或强制跨语言同形的自动化规则。
