# 跨层数据流思考指南

> 贯穿 React 前端、Go 业务服务、CGO 边界与 C++ 原生引擎的数据流安全核验。

---

## 跨层数据流四阶段自检矩阵

### 阶段 1：React 前端 ➔ Go 后端 API

- [ ] **参数双重强校验**：入参在前端经 Zod 校验，在后端经 Gin `binding` 声明式校验。
- [ ] **统一错误语义与后端 i18n**：前端请求携带 `Accept-Language`；后端返回已翻译的 `{ code: "VALIDATION_FAILED", message: "..." }`，前端直接通过 Toast 弹出展示。

### 阶段 2：Go 后端 ➔ CGO / C ABI 桥接

- [ ] **C ABI 句柄纯净**：传给 C 的句柄为合法不透明指针 `Zhulong_engine_h`。
- [ ] **严格指针合规**：传给 C 的内存绝对不包含 Go 堆指针；C 侧绝不跨调用持有 Go 指针。
- [ ] **成对释放守则**：所有 `C.CString` 均有紧邻的 `defer C.free` 释放。

### 阶段 3：C ABI 门面 ➔ C++ 原生流水线

- [ ] **全异常防爆**：ABI 导出函数使用 `try { ... } catch (...)` 包裹，禁止异常越界。
- [ ] **有界队列与背压**：视频流与事件受有界容量保护；AI 推理拥塞时丢弃旧帧，杜绝 OOM。

### 阶段 4：C++ 推理结果 ➔ Go 广播 ➔ 前端呈现

- [ ] **结果中立化**：C++ 检测框转为通用结构体，通过 SSE/WebSocket 序列化为 JSON 广播。
- [ ] **凭据脱敏**：流 URL 在日志和网络响应中脱敏掩码，禁止明文暴露。

## 定长预算的序列化切分（跨语言载荷硬上限）

当 Go 侧向 native 侧下发带硬上限的载荷（如 IPC 单包 64KB）并需自行切分时：

- [ ] **按测量字节装箱，不按条数**：固定条数（如「每片 10 条」）会随数据内容漂移。实测 512 维 L2 归一化 float32 特征 JSON 序列化约 **12.3 bytes/分量**（单条 ~6.3KB），「每片 10 条」在真实数据下产出 64204~65373 字节，距 65536 上限仅剩 **0.25%~2.0%** 余量。
- [ ] **保留预算余量**：以 `MaxIpcPayloadSize * 9 / 10` 作为切分预算，吸收头部宽度与序列化漂移。
- [ ] **头部按最坏宽度测量**：overhead 必须用**最宽**的头部（如 `ShardIndex`/`ShardTotal` 都取 6 位数）测量，而不是取 0/1，否则大底库时预算失效。
- [ ] **避免装箱循环内重复序列化**：先逐条测量一次（O(n)），再按 `overhead + Σsize + (n-1) 分隔符 <= budget` 算术装箱，否则 10k 条会产生数百 MB 临时 JSON。
- [ ] **单条超预算必须显式报错并携带可定位标识**（如 `face_id`），严禁静默丢弃——静默丢一条会让 native 侧底库与 DB 永久不一致。
- [ ] **测试数据必须用真实量级**：用 `float32(i*1000+j)` 这类整数特征序列化后比真实数据小 2.5 倍，会让「每片 <= 64KB」的断言**必然通过**，掩盖切分参数过大的缺陷。测试须用真实 ID 长度、真实特征量级，并断言 `<= 预算` 而非 `<= 硬上限`。
- [ ] **反向验证**：把实现回退到旧版本，确认新测试真的失败；只断言「能跑通」的测试无法证明它能抓住旧缺陷。
