# 代码复用与架构抽象思考指南

> 平衡“避免重复代码”与“避免过早过度抽象”。

---

## 1. 核心原则

1. **三代定律 (Rule of Three)**：
   - 第一次：直接实现，保持简单。
   - 第二次：允许局部重复，观察差异。
   - **第三次出现相同模式**：提炼公共抽象或下沉至 `shared/`。严禁预设庞大的未来抽象。
2. **单一真实源 (Single Source of Truth)**：
   - 全局常量（端口、协议枚举、超时阈值）只能在一个权威位置定义，禁止多处硬编码。

---

## 2. 经典反模式

| 反模式 | 危害 | 正确做法 |
| --- | --- | --- |
| **跨业务模块复制粘贴代码** | 修复 Bug 时局部遗漏 | 业务无关的通用解析下沉到底层基础包 |
| **散落的非结构化 JSON 解析** | 运行时 `as any` 导致崩溃 | 在前端切片 `api/` 层统一使用 Zod/强类型 DTO 一次性解码 |
| **提前建立空无一物的 `pkg/`** | 缺乏归属沦为垃圾场 | 坚持模块就近存放，单机系统代码全部收敛在 `internal/` |

---

## 3. 提交前复用审查清单

- [ ] 是否在无 2 处以上实际消费前就建立了公共抽象？
- [ ] 常量、枚举与错误码是否引用了权威统一定义？
- [ ] 提取的公共函数是否放置在清晰归属的包中，未破坏单向依赖？
