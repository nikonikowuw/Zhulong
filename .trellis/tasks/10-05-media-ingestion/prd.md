# 需求文档：媒体接入与流转管道

## 1. 目标 (Goal)

构建 Zhulong 系统核心的「媒体接入与流转管道（Media Ingestion Pipeline）」，横跨 C++ 原生引擎、CGO 桥接、Go 业务宿主与 React 前端：

- 实现基于内嵌裁剪版静态 FFmpeg 的高可靠 RTSP 码流拉取与解复用；
- 建立物理流单例连接池与统一多维引用计数，支持多个逻辑摄像机和算法任务对物理流与硬件解码器的高度复用；
- 提供两阶段探测门禁（Probe Gate）与指数退避断线自愈状态机；
- 支持主/子双码流解耦、解码保连续后级多速率抽帧、以及多算法同帧零拷贝共享；
- 实现按需 CGO 码流借用与 WebSocket 广播，配合前端 WebCodecs/MSE/WASM 三级自适应播放器，在服务端零转码前提下实现 H.264/H.265 毫秒级低延迟防弹预览。

---

## 2. 核心需求 (Requirements)

### 2.1 物理流单例复用与连接池 (Physical Stream Pooling)

- **R1.1 源解耦与去重**：允许用户创建多个逻辑摄像机或任务指向相同的 RTSP 地址。底层按规范化 URL（去除空格、格式化协议与端口）维护物理流会话池，同一物理流在底层只建立一条 RTSP 网络连接，且只分配一个 VPU 硬件解码器实例。
- **R1.2 统一多维引用计数**：每个物理流维护统一引用计数：
  $$\text{RefCount} = \text{AI 推理任务数} + \text{Web 实时预览人数} + \text{录像切片任务数}$$
  - $0 \rightarrow 1$：按需唤醒，发起 RTSP 握手与解码器初始化；
  - $1 \rightarrow N$：单条物理流在内存广播扇出给所有下游订阅者；
  - $N \rightarrow 0$：启动 5~10 秒 Grace Period 延时休眠防抖，倒计时期间若有新订阅者则直接复用；倒计时结束仍无订阅者则向 IPC 发送 `TEARDOWN` 优雅断开并释放缓冲池。

### 2.2 离线底座与流拉取 (Native Ingress & Codecs)

- **R2.1 自包含交付**：C++ 原生引擎通过静态内嵌裁剪版 FFmpeg（`libavformat.a`, `libavcodec.a`, `libavutil.a`），目标设备无需联网，零外部包管理器依赖。
- **R2.2 协议与码流支持**：支持 RTSP（TCP Interleaved 优先，UDP 可配置），支持 H.264（AVC）与 H.265（HEVC）原始码流解析，支持从 SDP/码流中提取 SPS/PPS/VPS 参数集。
- **R2.3 防吊死中断保护**：必须为 `AVFormatContext` 挂载 `AVIOInterruptCB` 超时机制，配置无数据读超时（默认 5s），杜绝网线断开或 IPC 宕机时 worker 线程永久死锁。
- **R2.4 凭据特殊字符与鲁棒解析 (Special Characters & RFC 3986)**：
  - 全面兼容摄像机密码中包含 `@`, `:`, `/`, `?`, `#`, `!`, `%`, `&` 等任意特殊字符的真实工业场景；
  - 提供前端结构化分字段输入（IP、Port、Username、Password）与单行完整 RTSP 智能逆向消歧解析（从后向前定位最后一个合法 `@` 符以剥离 userinfo）；
  - 对提取出的用户名与密码执行严谨的 RFC 3986 百分号转义（Percent-Encoding，如 `@` ➔ `%40`、`:` ➔ `%3A`），保证规范化 URL 可被 FFmpeg 底层正确解码并完成 Digest/Basic 鉴权；
  - 务实凭据安全策略：
    - **服务端日志强制单向脱敏**：终端标准输出、Zap 结构化日志与公开错误堆栈中的 RTSP URL 必须强制将密码替换为 `******`，杜绝日志打包排查或截图时明文密码泄露；
    - **已认证管理员掌控透明度**：既然已登录用户是系统唯一管理员主人，API 摄像机详情与 Web 界面应支持管理员查看明文密码（带小眼睛 👁️ 显隐切换）以及一键复制完整带凭据的 RTSP 地址，方便在 VLC 等外部播放器中直接排查调试流媒体，拒绝教条式黑盒屏蔽；
    - **数据库安全存储**：真实密码经由 AES-GCM 独立加密落库。

### 2.3 探测门禁与生命周期自愈 (Probe Gate & Self-Healing)

- **R3.1 入库前探测（Probe Gate）**：创建或修改摄像机配置时，执行异步快速探测（严格限制 3~5s 超时）。探测成功并提取到视频宽、高、编码格式（H.264/H.265）及实际帧率后方可生效落库；若探测失败（认证失败、连接超时）直接返回明确语义错误（如 `CAMERA_AUTH_FAILED`, `CAMERA_CONNECT_TIMEOUT`），杜绝错误配置污染流水线。
- **R3.2 四态生命周期状态机**：维护通道状态：`offline`（未启用/手动停用）、`online`（正常拉流）、`reconnecting`（断流自愈中）、`error`（不可恢复错误，如鉴权 401）。
- **R3.3 指数退避重连**：断流后状态切为 `reconnecting`，重连调度采用指数退避加随机抖动策略（1s $\rightarrow$ 2s $\rightarrow$ 4s $\rightarrow$ 8s ... 上限 60s），避免频繁握手触发 IPC 防火墙封禁 IP；状态变更通过系统事件通道（SSE）实时通知前端。

### 2.4 算力节流与多速率抽帧 (Multi-Rate Decimation)

- **R4.1 主/子双码流解耦**：摄像机支持配置主/子双码流。子流用于全帧率轻量分析（周界防范、人形检测）与多画面预览；主流用于高清细节任务（人脸识别、车牌识别）与无损录像。
- **R4.2 解码保连续性**：硬件解码器（VPU）必须按完整 GOP 连续解码，保持 DPB 参考帧链完好无损，严禁在解码前随意丢弃 P 帧导致绿屏/花屏。
- **R4.3 任务多速率抽帧**：任务内各算法支持独立配置检测帧率（如翻越 10fps、安全帽 5fps、烟火 1fps）。在解码器出口后挂载节流步长阀（$\Delta t \ge 1/\text{FPS}$），非采样帧直接释放，不进入前处理与 NPU 推理，节省 80% 以上算力。
- **R4.4 多算法同帧零拷贝**：同一帧被多个算法认领时，通过 `std::shared_ptr<const Frame>` 零拷贝共享像素内存；相同输入尺寸的算法共享前处理生成的 `std::shared_ptr<const Tensor>`。

### 2.5 多消费者背压隔离 (Backpressure Isolation)

- **R5.1 码流级分流**：
  - 录像消费者：直接在 `CaptureNode` 获取原始 `AVPacket`，写入大容量有界队列（60~120 包），由独立线程封装写入 MP4，零解码消耗，绝不丢帧；
  - AI 推理消费者：解码后进入极浅 Frame 队列（容量 2~3 帧），若 NPU 拥塞直接丢弃最老帧（Drop-Oldest），保障分析永远针对最新画面。

### 2.6 Web 实时预览与前端全场景播放 (Web Real-Time Preview)

- **R6.1 服务端零转码透传**：服务端坚决不转码，直接将 H.264/H.265 的压缩码流（Packet）通过 WebSocket 转发给浏览器客户端，由用户终端 GPU 硬件解码。
- **R6.2 按需 CGO 借用桥接**：仅在有 Web 客户端建立 WebSocket 连接时，Go 侧通过 `cgo.Handle` 注册订阅；C++ 收到 Packet 回调 Go，Go 仅使用 `unsafe.Slice` 在调用期间借用数据广播至 WebSocket Hub，C++ 管内存释放；无客户端预览时 CGO 调用为零。
- **R6.3 前端三级自适应播放器**：前端集成支持 H.265/H.264 的防弹播放器（Jessibuca 模式）：
  1. 第一梯队：WebCodecs GPU 硬件解码优先（延迟 < 300ms）；
  2. 第二梯队：HTML5 MSE 硬件解码；
  3. 第三梯队：WASM SIMD 软解兜底（老旧机器与无显卡驱动环境保底播放）。

### 2.7 前端功能切片与独立导航解耦 (Feature Decoupling)

- **R7.1 独立一级菜单解耦**：严禁将设备管理与视频监视混杂在同一个臃肿视图中；前端必须提供独立的两个一级导航入口：
  1. **实时预览 (Live View · `/live`)**：专注于视频监视与作战大屏，提供 1/4/9 多画面网格布局、全屏放大、AI 实时检测框流式叠加；
  2. **摄像机管理 (Camera Management · `/cameras`)**：专注于运维配置，提供设备列表表格/卡片、增删改查、入库前 3~5s 异步探测门禁弹窗、明文密码显隐切换（👁️）、一键复制完整 RTSP 地址与连接诊断自愈操作。
- **R7.2 模块化代码切片隔离**：遵循架构规范，将管理与预览拆分为两个互不穿透的特性切片：`web/src/features/camera/`（负责设备元数据、CRUD 表单与状态感知）与 `web/src/features/live/`（负责多画面网格、播放器调度与 WebSocket 实时流）。
- **R7.3 前端多窗口单例流复用与引用计数 (Frontend Stream Multiplexing & Local Ref-Count)**：
  - 支持在多画面分屏（1/4/9 宫格）中，用户在不同窗口中重复选择同一台摄像机并行播放；
  - 该复用逻辑与引用计数**纯在前端客户端维护，严禁引入后端**；
  - 前端建立基于 `cameraId` 的单例连接池：首个分屏挂载（$0 \rightarrow 1$）才向服务端发起一条 WebSocket 连接；后续重复选中的分屏窗口（$1 \rightarrow N$）直接复用已建立的流对象并共享解码帧渲染，避免在同一浏览器标签页产生重复的 WebSocket 连接与网络带宽倍增；
  - 窗口卸载或切换时引用计数递减，当所有分屏窗口均不引用该摄像机（$N \rightarrow 0$）时，前端自动切断对应 WebSocket 并销毁解码资源。

## 3. 非功能性约束 (Non-Functional Requirements)

1. **单二进制交付**：Native C++ 静态库吸纳裁剪版 FFmpeg，最终整体静态/动态内联链接进单个 Go 二进制，零外部运行时目录依赖。
2. **CGO 指针与内存规范**：严格遵守 `cgo-contract.md`。禁止在 C 侧缓存 Go 指针；Go 侧切片借用使用 `unsafe.Slice` 并在调用期间完成复制，不得跨调用持有底层 C 指针。
3. **延迟与性能基线**：Web 预览局域网端到端延迟 $\le 400\text{ ms}$；无人查看且无 AI 任务时，摄像机通道物理连接与解码完全静默休眠，CPU 占用 $\le 0.5\%$。
4. **凭据安全与日志脱敏**：摄像机密码经 AES-GCM 加密落库；Zap 日志与异常追踪强制脱敏为 `******`；已认证管理员会话享有完整查看与复制权限。

## 4. 验收标准 (Acceptance Criteria)

- [ ] **AC-1 (物理流复用与引用计数)**：添加 2 个指向相同 RTSP 地址的逻辑摄像机并分别创建预览/任务，抓包或日志验证底层仅发起 1 次 RTSP 握手且仅分配 1 个解码器实例；关闭所有预览后，验证 5~10s Grace Period 期间刷新能秒开，倒计时结束后物理连接正常释放断开。
- [ ] **AC-2 (两阶段探测门禁)**：向 `POST /api/v1/cameras` 提交错误密码或不可达 IP，验证 3~5 秒内返回对应 4xx 语义错误且不启动后台死循环；提交正确地址则探测出真实分辨率与 H.264/H.265 编码并成功入库。
- [ ] **AC-3 (自愈重连与防封禁)**：拔掉测试摄像机网线，验证系统状态在 5s 内切为 `reconnecting`，重试日志呈指数退避（1s, 2s, 4s...），插回网线后在下一重试周期自动恢复为 `online`，视频流自动恢复。
- [ ] **AC-4 (多速率抽帧与画面完整性)**：配置 5fps 的分析任务，验证解码器输出完整 GOP 画面无花屏马赛克，同时 NPU 仅以 5fps 频率被调度，被丢弃帧显存即时回收无泄漏。
- [ ] **AC-5 (Web H.265/H.264 预览)**：在 Chrome、Safari 浏览器下访问 Web 控制台，分别测试 H.264 与 H.265 摄像机，均能正常出画，延迟 $\le 400\text{ ms}$；关闭浏览器标签页后，Go 侧 WebSocket 连接注销且 CGO 回调注销。
- [ ] **AC-6 (工程规范与测试通过)**：`make check` 全项通过（Native CTest 覆盖复用池与生命周期测试，Go `go test -race` 覆盖 CGO 订阅与 WebSocket Hub）。
- [ ] **AC-7 (特殊字符凭据鲁棒接入与安全平衡)**：针对包含特殊字符的凭据（如 `admin:Admin@123!@192.168.1.64:554/...`）进行接入与探测测试，系统能正确消歧义、完成 RFC 3986 转义并成功建立 RTSP 握手；日志输出严格脱敏为 `rtsp://admin:******@192.168.1.64:554/...`；已登录管理员在控制台详情中可切换显隐查看明文并成功一键复制完整 RTSP URL。
