# GB28181 设备接入与实时预览

## Goal

Zhulong 作为 SIP 服务端（UAS），接受下级 GB28181 设备主动注册，同步设备目录，
并能对指定通道发起实时点播、在现有预览链路中出画。

## 目标形态与质量等级

P0 交付形态已定：**单机、单网卡嵌入式小盒，无人值守 7×24、现场无运维**。
因此本任务的质量目标是「工业可用」而不是「演示能出画」，验收以可测指标为准（见末节）。
三条判定原则：

1. **合规以明确标准档为界**：P0 只声明 `standard` profile（GB/T 28181 信令 + Digest 认证 + 明文媒体）。
   GB 35114（A/B/C 级）不在 P0 实现，仅在架构上保留插入点，详见「合规档位」。
2. **容量必须拆成两个数**：「并发点播/解复用路数」（受 CPU + 媒体端口池限制）与
   「并发解码路数」（受 SoC 硬解能力限制）不是同一个指标。P0 只承诺前者，
   后者须实测后单独公布，不得在文档或界面中混用。
3. **故障必须自愈且可观测**：断电、拔网、IP 变更、时钟跳变、设备反复上下线都属于常规事件，
   不得需要现场人工介入才能恢复。

### 合规档位（GB 35114 判定）

GB 35114-2017《公共安全视频监控联网信息安全技术要求》与 GB/T 28181 配套，分三级：
A 级为信令身份签名，B 级在 A 级上增加视频内容签名，C 级在 B 级上增加媒体流加密。
公安/政法视频专网、雪亮工程类项目会强制；园区/厂区自用一般不会。

**P0 决策：不实现 A/B/C，只保留接缝。** 升级触发条件与确认方式：

- 触发信号：技术规格书或招标文件出现 `GB 35114` / `SM2` / `SM3` / `SM4` / `数字证书` /
  `视频签名` / `接入公安视频专网` 任一词，或甲方确认需接入此类专网。
- 出现触发信号时重新评估范围，不沿用本 PRD 的 P0 结论。
- 本 PRD 对三级的描述只用于判定工作量量级，**不构成合规依据**；
  条款细节（签名覆盖范围、报文封装结构、密钥协商流程）以标准正文为准。

已知代价（若将来升级）：A 级需证书体系 + SIP 报文签名封装（与普通 28181 报文不兼容），
C 级还必须改 Native 媒体路径（解密先于解复用），且需实测小盒 SoC 的 SM4 吞吐能否支撑目标路数。

## 已确认决策

1. **角色**：Zhulong 接受设备 REGISTER/MESSAGE（本事务中作为 UAS），并作为 UAC 向已注册设备发起点播 INVITE。P0 不做向上一级平台级联；该排除项不排除点播所需的出站 UAC 对话。
2. **P0 验收线**：必须做到「点播后预览出画」，不接受只交付信令面或设备清单。
3. **域归属**：GB28181 通道复用 `internal/camera` 域，`protocol=gb28181`，
   URI 形态 `gb28181://<deviceId>/<channelId>`；预览、感知记录、AI、诊断共用现有链路。
4. **分层切法**：Go 侧 `internal/gb28181` 只做信令与端口/会话编排，不碰媒体字节；
   原生 Engine 新增 GB28181 输入源（RTP 收包 → PS 解复用 → H264/H265 ES → 汇入现有 PreviewNormalizer）。
5. **媒体解析策略**：优先复用固定版 FFmpeg 的 MPEG-PS demuxer。S3 必须先用已绑定 UDP fd 做 PoC，比较 FFmpeg RTP 输入路径与「有界 RTP 重排/拼接 + 自定义 AVIO + MPEG-PS demuxer」是否满足 fd 所有权、取消和首包非阻塞要求；根据可复现证据选定一条路径。除非真实样本证明 FFmpeg PS demux 不可用，否则不自研 PS 解包器；未验证的私有 RTP 扩展不得默认剥离。
6. **通道入库策略（方案 C）**：`gb_channels` 只存设备侧原始清单，用户显式「添加为摄像机」后才写入
   `cameras`。不使用自动创建，避免绕过凭据加密与原子探测门禁、并让 AI/记录意图保持显式。
7. **注册安全（默认采纳）**：强制 SIP Digest 密码，每设备一份，复用现有 `camera.key` 加密存储；
   不放行匿名注册（`require_registered_device = true`）。为使 allowlist 可用，P0 必须提供受保护的设备预置/凭据维护入口；首次 REGISTER 前远端地址未知，持久化模型允许 `remote_addr` 为空。首版提供单设备手工录入；批量导入不作为门槛。
8. **按协议特征处理，不按设备自报版本串分支。** 字符集、媒体编码和传输层根据实际字节/协商结果判断；设备自报的版本串只用于诊断。GB/T 28181-2016/2022 的具体差异表是待标准核对的实现假设，不据此宣称完整版本合规；S1/S3 必须以标准正文和报文样本验证涉及的字段与编码行为。
9. **运行配置**：P0 用 SQLite 单例 `gb28181_configs` 和系统设置 UI 配置；该表为唯一事实源，`config.toml` 不重复保存 GB28181 参数。配置保存后不热应用，UI 明确显示“需重启生效”。
10. **单网卡媒体承载（形态决策）**：媒体只会绑定一个本机地址，`media.bind_address` +
    `media.advertised_ip` 单值即可。无 NAT 时 `advertised_ip` 允许留空并由唯一非回环 IPv4 推导；
    检测到多个 IPv4 或存在 NAT 时必须显式配置，推导失败不得跨网段写入 SDP。
11. **媒体端口成对租用（RTCP 定案）**：每路会话租用 **RTP + RTCP 一对**端口，
    RTCP socket 由 Go 侧持有并只收不解析。理由：SDP 宣告 RTCP 端口却不 bind 时，
    部分设备收到 ICMP port unreachable 会静默停流，现场表现为偶发黑屏、重连才恢复。
    101 端口池 → 50 路并发点播，与本形态容量匹配。
    SDP 具体形态（m 行是否携带 RTCP、`y=`/`f=` 行语义）须在 S3 以标准正文与设备夹具核验。
12. **RTP over TCP 媒体面移出 P0**（修订原排除项）：P0 只做 UDP 媒体，前提是设备与盒子同侧局域网。
    一旦出现盒子外侧 NAT 后的设备，该前提失效，须重新评估把 RFC 4571 纳入范围。
    该条件写入验收前置说明，不允许在部署文档中省略。
13. **并发点播 ≠ 并发解码**：P0 承诺「并发点播/解复用路数」；解码路数受 SoC 限制，
    须在目标硬件实测后单独给出并与点播数分开表述。
14. **安全基线进 P0**：SIP 报文大小上限、XML 大小/深度/外部实体防护、REGISTER/UAC 限速、
    nonce 防重放窗口，全部作为 P0 交付项而非加固项。
15. **可观测进 P0**：每会话结构化日志带 `device_id` / `channel_id` / `session_id` /
    `sip_call_id` 关联字段；提供运行态快照（在线设备数、活动会话数、端口占用、首帧耗时、
    丢包计数、失败原因分布）。不引入外部 TSDB 依赖，快照经现有 protected API 暴露。
16. **异常环境自愈进 P0**：网卡 IP/DHCP 变更、系统时钟跳变、设备反复上下线、
    SIP listener 异常退出，都要有检测与自动恢复路径，且不得阻塞 Web 管理面。
17. **端口耗尽必须显式失败**：端口池无可用端口时返回稳定错误码并计入运行态，
    禁止静默等待或复用他人端口。

## 硬约束与风险

1. **单网卡简化与 NAT 例外**：`media.bind_address` 是本机可绑定地址；`media.advertised_ip` 是设备可达
   且写入 SDP 的地址。单网卡无 NAT 时可自动推导，多 IPv4 或 NAT 场景必须显式配置；
   公网地址不要求出现在本机网卡上，不得因不可推导而静默使用错误地址。
2. **媒体端口成对租用（已定案）**：每路会话占 RTP+RTCP 两个 socket；ABI 只接收 RTP fd，
   RTCP 由 Go 侧读丢弃。端口池、SDP、回收测试与容量模型都必须按「2 端口/会话」计算。
3. **SIP 5060 不需要低端口 capability**：默认端口 5060 大于 1024；只有管理员改配到 1024 以下的端口时才需要 `CAP_NET_BIND_SERVICE` 或相应权限。
4. **引擎去重键是规范化 URI**（`ingestion-contract.md` §3.4）：GB28181 每次点播是新 RTP 会话，
   URI 相同而会话不同，去重与 8 秒宽限期语义必须重新定义，否则重连会复用已死的 socket。
5. **创建时的原子探测门禁不成立**：不能 DESCRIBE 一个尚未 INVITE 的通道；通过已同步目录显式添加摄像机，首帧媒体信息用于后续校正。
6. **字符集容错**：设备 XML 的声明不可信；先严格验证 UTF-8，失败时回退 GB18030。标准要求和厂商实际行为均须用报文样本验证。
7. **ABI 演进**：只能尾部追加字段，`ZHULONG_ABI_VERSION` 与 Go 侧 `expectedABIVersion` 同步。
8. **版本号不可信**：分支条件必须是协议特征，不能是设备自报的版本串。
9. **重启生效语义**：配置保存只更新持久化目标值，不热切换已绑定的 SIP/RTP socket 或现有 SIP 服务。GET/PUT 返回目标配置、进程启动配置和 runtime 状态；`restartRequired` 由两份配置比较得到，不单独持久化。进程重启并加载目标配置后，标志清零；listener 启动错误单独通过 runtime 状态显示。
10. **密钥完整性检查覆盖 GB 凭据**：启动时判断 `camera.key` 是否可丢失，必须同时检查摄像机流密文和 `gb_devices.encrypted_password`；只有 GB 密文的数据库也不得静默生成新密钥。
11. **小盒资源预算**：解复用、解码与 AI 推理共享同一 SoC；每会话接收缓冲必须有硬上限，
    不得随包累积。fd 预算需覆盖 100 设备 TCP 连接 + 50 会话 × 2 端口 + 引擎自身。
12. **IP/时钟是常规故障**：DHCP 换址会让注册与媒体地址同时失效；断电重启会让 PS 时间戳跳变。
    两者都必须有检测与可诊断失败路径，不能表现为「设备在线但黑屏」。
13. **端口池容量即并发上限**：`rtp_port_min..max` 决定并发点播上限（2 端口/会话）。
    修改范围属于需重启生效的配置；耗尽的错误码与计量必须进入运行态快照。

## 验收标准

### 功能

- [ ] 预置设备 Digest 凭据后，真实设备（至少 1 个厂商型号）能完成 UDP、TCP REGISTER；设备重新注册后恢复 online。Zhulong 重启后的持久化记录在收到新鲜有效 REGISTER/Keepalive 前不得显示 online
- [ ] 设备目录同步入 `gb_channels`；通道只在用户显式添加后出现在摄像机列表
- [ ] 对已添加通道发起点播后，WebSocket 预览出画；`dts_us` 按解码包序单调，`pts_us` 按预览契约保留显示顺序，可因 B 帧重排回退
- [ ] 最后一个预览/AI 媒体消费者离开后，宽限期内重连复用会话；宽限期到期后发 BYE，Native fd 停止并关闭后端口才归还；重复点播 10 次无端口泄漏
- [ ] 设备断电 / 心跳超时后状态转 offline，恢复后自动重新可点播
- [ ] 配置 UI 保存后数据可从 SQLite 读回；当前运行配置不变且显示“需重启生效”，重启后应用新配置并清除提示
- [ ] `make check` 全绿；新增 Go 逻辑有表驱动测试，原生新增路径有对应 C++ 单测

### 容量（单机单网卡小盒，目标板实测）

- [ ] 100 台设备注册 + 1600 条通道目录入库可完成，目录同步期间管理 API 响应不劣化到不可用
- [ ] 并发点播 50 路（端口池 101 端口 ÷ 2）可同时建立并各自出画；第 51 路返回稳定端口耗尽错误码而非挂起
- [ ] 首帧时延：同网段 INVITE→首帧 P95 ≤ 3 s；10 s 内无有效媒体转 FAILED 并释放资源
- [ ] 并发解码路数单独实测并写入部署文档，不与会话数混用

### 稳定性与自愈

- [ ] 72 h soak（50 路循环点播）：RSS 增长 < 5%，fd 与端口零泄漏，无 goroutine/线程累积
- [ ] 1000 轮点播-断开-回收循环后端口池占用回到基线
- [ ] 设备断网 30 s 后恢复网络，能重新 REGISTER/Keepalive 并再次点播成功
- [ ] DHCP 换 IP 后系统检测到变更：既有会话被清理/告知需重启，且不出现「在线但黑屏」的静默状态
