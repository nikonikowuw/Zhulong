# 算法插件架构：技术设计（待最终审阅）

## 1. 结论与设计边界

**不用要求所有算法跨动态库继承同一个 C++ 基类。** 对外定义版本化 C ABI，内部允许 C++ 继承/组合；独立 `.so` 由通用原生 runner 在独立进程中加载，并调用公共算法运行库复用模型/执行资源管理。每个包进程共享兼容的模型资源组，每个 Worker 独占执行上下文和可变内存。

本文落实 `prd.md` R1–R12。用户已选择公共库同时统一推理资源管理，并明确开发期单文件、单次推理的黑盒验包不评判算法精度；接口名称、目录、协议及初始参数仍是技术建议，不是已存在 API；当前不新增产品文件。板端 SDK 与模型证据未齐，设计就绪不表示 RKNN 共享、零拷贝或性能已验证。

技术收口建议：一台设备上，一个包 ID 同时只运行一个活动版本/进程；同包的多个摄像机任务共享该进程，任务状态彼此隔离。一个包可含多个模型，但只在同一模型内容、设备和兼容执行配置内共享权重；不同模型不能混用资源。版本目录可保留 current/previous/pending，但不同时运行新旧进程。多设备部署仍是每台设备独立运行，不引入跨设备共享模型服务。

SDK 首个开发/测试样例使用仓库既有 C++17；公开 C ABI 不要求调用方使用 C++，也不额外承诺 Python 等托管运行时集成。性能不预填 FPS：worker 数有界、通过目标板对照测试选定，不把多线程当成 NPU 多核。

## 2. 系统分层和依赖

```text
Go 宿主
  ├─ 包管理：登记/配置、期望状态、启动/退出监控、升级/回滚
  ├─ 公共业务入口：消费感知结果；跟踪/规则/事件能力不在插件重复实现
  └─ internal/engine → 既有纯 C ABI → Native 采集/解码与 FrameBroker
                                      │
                  Native 帧通道 IPC ──┼──→ Runner A → A.so
                                      │      ├─ ModelGroup
                  Go 控制/结果 IPC ───┤      └─ Worker[0..N)：独立 Execution
                                      └──→ Runner B → B.so
```

- **包管理不等于算法代码**：宿主不 `dlopen` 插件，包括查询元信息/探测阶段也不在宿主执行插件构造器。
- **runner 不等于模型后处理库**：runner 管装载、协议、Worker 调度与生命周期；感知插件决定前处理、模型执行和后处理语义，但可调用公共库，不要求每包重写其通用实现。
- **公共层不等于全部塞进 Go**：Go 负责控制/持久化/业务协调；高频公共计算可在后续 Native 节点中实现。当前任务只定义感知结果入口，不实现完整跟踪规则引擎。
- **像素不绕 Go**：帧流从 Native broker 送到原生 runner；Go 接收有界结构化结果及状态，不逐像素/逐框 CGO 调用。

建议目录（实施时按需创建，当前不创建空目录）：

| 位置 | 职责 |
| --- | --- |
| `internal/algorithm/` | 包进程管理、状态与版本记录；不依赖 `internal/app` |
| `internal/app/` | Fx 装配和应用生命周期接线，不放算法实现 |
| `internal/engine/` | 对 broker 管理的 Go 原生类型封装；业务包不 `import "C"` |
| `native/src/algorithm/` | runner 装载、线程池、IPC 适配与示例宿主，不含具体感知逻辑 |
| `native/src/algorithm/runtime/` | 公共库的中立实现，按实际复用点添加，不另建调度线程池 |
| `native/src/pipeline/` | 帧广播/有界投递与 lease 生命周期，对具体算法和 SDK 保持中立 |
| `native/src/backends/rknn/` | Rockchip 适配代码，链接进公共运行库目标，不把 RKNN 带进 Go 主宿主 |
| `native/sdk/` | 可单独分发的插件/公共库纯 C 头文件、C++17 可选薄封装与独立构建样例 |

`include/Zhulong/engine.h` 仍是 Go/CGO 唯一原生入口。插件 SDK 是 runner 与外部开发者的另一份接口，不能拿现有 C++ `frame.hpp` 作为插件二进制合同，也不向宿主暴露厂商头文件。各算法工程不链接宿主私有 `ZhulongEngine` 类实现。

### 2.1 公共算法运行库：工具与推理资源统一封装

用户已选择方案 2：公共 `.so` 不只提供图像/数学工具，还统一模型加载、worker 上下文、缓冲和正常/失败清理。建议命名为 `libzhulong_algo_runtime.so.1`（名称和 ABI 主版本仅示意），让独立插件调用它，而不是把所有算法合并成一个大 `.so`。独立交付约束的是算法发布边界，不要求复制上述公共实现。

```text
进程 A：runner → A.so → libzhulong_algo_runtime.so.1 → 经验证的 RKNN/RGA 适配
进程 B：runner → B.so → libzhulong_algo_runtime.so.1 → 经验证的 RKNN/RGA 适配
                  各进程保持自己的模型组、worker 执行资源和任务状态
```

| 操作 | 推荐归属及边界 |
| --- | --- |
| 进程启动/恢复/升级 | Go 包管理；不下沉到公共算法库 |
| 插件装载、IPC、线程池、任务分派、帧 lease ACK | 通用 runner；不让各插件或公共库再复制一套调度器 |
| 模型加载/查询、执行上下文创建/销毁、同步推理调用与完成等待、私有 I/O/workspace、失败清理 | 公共库及其后端；插件决定执行哪些模型，共享模型资源与 worker 私有资源分离，设备权重共享仍须实测 |
| resize、颜色转换、letterbox 与坐标还原等可复用操作 | 公共库按真实消费点提取；插件明确选择参数，库校验 format/plane/stride，不猜归一化或模型输入合同 |
| NMS、几何运算等后处理工具 | 有实际重复时抽取；阈值、类别策略和算法变体显式指定，不默认所有模型共用一种后处理 |
| 模型选择、模型特有 tensor 解析、多模型编排、感知语义 | 独立插件；可以调用公共操作，也允许必要的定制实现 |
| 通用跟踪、业务规则、事件管理 | 原定公共业务层；不因“公共库”这个名称把它们塞回感知插件依赖 |

SDK 与公共 `.so` 不是二选一：SDK 是开发交付物，包含头文件、链接所需文件、构建样例和文档；公共 `.so` 是其中供目标机运行的实现。可用编译进各插件的 C++17 薄封装统一默认生命周期、异常转换和 C ABI 导出样板。跨库仍为版本化 C ABI + 不透明句柄；不暴露 C++ 基类虚表、STL 或 RKNN 对象，不为简化插件而创建一个覆盖所有模型的万能基类/配置 DSL。

公共库不持有未受控的全局可变推理上下文。每个模型组有自己的句柄和共享资源，每个 worker 有独占执行句柄/缓冲；runner 仍在 worker 所属线程调用创建、处理和销毁。插件选择并组合能力，通用错误清理由公共实现负责，不能因复用库而省略部分初始化失败回滚。

**共享 `.so` 不等于共享模型内存：** 不同进程映射同一个库文件时，其可共享的只读代码页可能被操作系统复用；可写全局变量、堆、执行上下文和设备权重不会因此跨进程自动共享。同包同模型的线程间权重共享继续受 §6 约束，不新增跨包模型共享服务。是否节省物理内存必须另测，不能从 NEEDED 列表得出。

该选择减少资源管理样板代码和所有权错误，代价是承担公共库/厂商版本维护责任。当前仓库尚无真实算法实现可供抽取；实施时按规范从实际消费点提炼，用独立样例检验接口，不预建庞大通用库。仅复用图像或数学函数不足以满足 R11，模型/执行生命周期和缓冲管理也必须由公共实现承载。

### 2.2 公共库交付、兼容和回滚（技术建议）

| 方式 | 收益 | 代价 |
| --- | --- | --- |
| SDK 静态辅助库 `.a`，链接进每个算法 `.so` | 同一份源代码可复用，少一条目标机动态依赖；是最小交付方案 | 修复公共实现后，受影响插件通常需重新链接/发布；各包可能携带重复机器码 |
| 独立公共 `.so`（本方案采用） | 公共实现独立构建；ABI 和语义兼容时，可不重编插件而采用修复版 | 多一套 ABI/能力协商与依赖版本发布、验证和回退责任 |

静态辅助库仅保留为取舍对照，不作为替代公共动态运行库的首期交付目标。公共 `.so` 首期建议使用普通动态链接依赖，不同时引入另一套服务注入协议。插件 ABI 与公共库 ABI 分别演进；双方遵守 §4 的版本/结构容量、错误返回和所有权规则，不能只凭相同 SONAME 宣称兼容。

- 公共库以不可变版本目录发布。每个包记录要求的 ABI/能力和实际验证、选用的库构建身份；启动从受控依赖位置解析，不依赖开发机的全局 `LD_LIBRARY_PATH`，检查传递依赖，禁止缺库时静默回退到另一份系统库。
- 同一 runner 进程只使用其选定的一套公共运行库，不混用不同版本的句柄/释放器。不同包可继续选择各自已验证的公共库版本；厂商 Runtime 与驱动的兼容及并存能力另外验证，不因普通 ELF 库可并存就推定成立。
- 公共库更新不自动改变正在运行进程的代码，也不强制所有算法包同时升级。先发布并测试新依赖组合，再按包安全重启采用；旧依赖留存至不再被运行进程或回退记录引用，禁止原地覆盖或运行中卸载。
- previous 回退集合不仅包含插件/模型/配置，也包含其公共库依赖身份；恢复旧插件却加载新库不算完整回滚。保留 R7–R9 的单包停启、资源安全门和有界回滚。
- 公共库分配的模型/执行句柄和缓冲只能经该库对应接口释放；插件自有结果仍由插件释放。runner 只调用插件公开销毁接口，插件再委托实际分配者，不能跨库猜测 `delete/free`。借用输入继续由 Native/broker 管理，不转移给公共库。

验证公共库方案时，至少两个独立插件应通过同一公共实现管理模型资源、执行上下文和缓冲，覆盖独立状态、部分初始化失败回收、公共库缺失/不兼容、单包依赖升级与回退；检查 ELF 依赖和实际加载路径。可先用硬件无关夹具验证生命周期机制，但不证明 RKNN/RGA 功能或性能已经可用。

### 2.3 独立单次黑盒验包：合规与可运行性，不判精度

R12 将开发者独立运行的最小范围收敛为：指定一份有效测试输入文件，经适配形成一次合法的帧请求，调用同一插件的标准 `process` 路径一次。该请求内的多模型编排仍由插件决定，不把“一次”误写成限制厂商 API 只能调用一次。无需启动 Go、数据库或摄像机业务服务，不扩展为目录批测、视频/RTSP 独立服务或精度评测平台。

建议 SDK 提供统一验包入口，复用 runner 的插件装载、资源生命周期和执行路径；文件读取/输入适配在 runner 侧实现，不要求每个算法 `.so` 另写 `main()`、图片解码或专用自测接口。算法作者提供自己的包、配置及匹配输入合同的样本，不需要给平台提供预期检测框或精度阈值。具体文件格式按输入能力和模型合同选择，不承诺任意文件可直接推理。

```text
静态包检查 → 启动被监督的 runner → ABI 查询、创建模型/worker/任务
→ runner 输入适配器读取指定样本 → process 一次
→ 校验结果协议并释放结果 → 关闭任务/worker → 销毁模型 → 汇总验包报告
```

验包命令的监督侧只负责状态/退出监控和有界等待；所有插件代码，包括 ABI 查询，都在被监督的 runner 中执行。不能只做 `dlopen`，也不能把插件单独返回一个“自测成功”标志当成标准推理路径已完成。只创建一组烟测所需资源，不顺带启动常驻采集或无限重试。

| 检查情况 | 验包判定 |
| --- | --- |
| 包/资源缺失、ABI 或依赖不兼容、模型/worker 初始化失败 | 不通过，报告实际失败阶段 |
| 样本不存在、损坏、不受支持或不符合声明的输入合同 | 不能判通过，单列测试输入错误，不混同为算法崩溃；不替换成任意全零输入 |
| 标准推理调用成功，结果符合 schema、大小上限与所有权合同 | 该次契约烟测通过；检测类的合法空结果也通过 |
| 输出协议合法，但识别类别/位置等与人的预期不符 | 不影响契约烟测；明确标记未评估算法语义/精度 |
| 推理返回错误、崩溃、超时、输出协议非法或清理失败 | 不通过；不能伪装成“未检出” |

“结果协议合法”包含必需字段、类型、长度/数量上限、输入关联和声明的数值约束，不要求非空检测或达到某个置信度。结果内容可以提供给开发者自行检查，但无需标注数据、ground truth、精度/召回率比较。算法作者可以在自己的工程追加精度测试，不由平台通用验包器判定。

独立输入缓冲由 runner 的文件输入适配器分配/管理，插件只读借用，存活至少覆盖同步 `process`；结果由插件的 `result_release` 释放，公共库句柄/缓冲经公共库对应接口释放。沿用所属 worker 线程清理、join 后销毁模型组的顺序。监督侧超时或子进程退出不证明 DMA 已清理，仍遵守 §5.2 的资源安全门。

报告区分包/ABI/初始化/入口调用/输出协议等检查项，并明确未做精度评估。纯黑盒成功返回不能证明内部执行了指定模型或全部算子都在 NPU 上运行；在公共运行库可提供本次请求关联的后端完成证据时记录该证据，否则只报告入口调用完成，不能冒称硬件已验证。首期仍限可信团队插件，不新增针对恶意插件的执行证明机制。

这项单次烟测不替代 AC5 的后端工程正确性、权重共享、并发与长期稳定性验证，也不证明算法精度。离线测试通过不替代正式进程当前代次的 READY；启动/升级若复用这条检查路径，仍按 §7 在正确代次及安全停旧顺序内执行，不提前并存新旧模型。目标平台、SDK/驱动、模型/量化证据门继续有效。

## 3. 插件包与兼容性

建议包包含 manifest、插件 `.so`、模型文件、只读资源及配置约束说明。manifest 最少声明包 ID/版本、插件 ABI、入口相对路径、模型/资源身份、支持的目标架构/运行时及输入输出能力。公共库依赖按 §2.2 记录 ABI/必需能力及已验证依赖身份；受控公共库位置由安装管理解析，不允许插件借此任意访问包外路径。

- 版本目录不可原地覆盖；资源相对路径不得逃逸包根目录，不跟随指向目录外的链接。控制文件数量、字节总量和单文件上限。首个机制验证可用受控目录安装，不顺带开发 Web 上传平台。
- 宿主只做不执行代码的元数据/完整性检查，runner 再执行 ABI 查询、模型加载和就绪检查。哈希只是完整性证据，不冒充来源认证或沙箱；来源限定为受信任发布流程。
- C ABI 解决接口/类型边界，不消除 CPU 架构、用户态 ABI、libc/libstdc++、RKNN Runtime/驱动和模型目标的兼容要求。
- 同主版本可追加可选字段/函数，必须通过版本与 `struct_size` 协商；未知必需能力或主版本不符拒绝装载，不能靠猜测继续。
- 模型、配置、结果 schema 均关联版本/身份，回滚必须连同上次成功配置恢复，不能拿新配置硬套旧插件。

## 4. 进程内 C ABI 契约

建议通过一个查询入口取得函数表，表中只含固定宽度整数、显式长度、纯 C 数据视图、函数指针与不透明句柄；不暴露 STL、虚表、异常或厂商 context。自然对齐并通过 C/C++ 编译和布局测试冻结，不依赖 `#pragma pack` 掩盖 ABI 问题。

| 概念操作（名称示意） | 契约 |
| --- | --- |
| `get_api` | 纯 C 导出，校验 ABI/表容量，返回可调用能力；函数地址只在库仍加载时有效 |
| `model_create` / `model_destroy` | 创建/销毁该包的共享模型资源组，可含多个不同模型的独立资源；不据此保证厂商物理权重共享 |
| `worker_create` / `worker_destroy` | 从模型资源组建立/回收一个执行实例，输入输出、workspace 与临时区独占 |
| `task_open` / `task_close` | worker 内注册/释放任务状态；无状态算法可作轻量实现，任务停用后不得永久积累状态 |
| `process` | 处理一个任务的一帧，输入只读借用，返回结构化结果和状态；参考合同为同步完成，不在返回后偷偷继续使用借用输入 |
| `result_release` | 由产生结果的插件释放其结果内存；同一 worker 下次处理前完成序列化与释放 |

调用规则：

1. 进程控制线程串行装载/销毁模型组；每个 worker 在所属线程创建、使用和销毁执行资源。派生上下文时对共享根资源的操作串行化，不假定复制接口可并发调用；若 SDK 有额外线程绑定要求，按版本合同实现并验证。
2. 每个执行实例同一时刻只处理一个任务；并发靠多个实例，不共享可变 I/O 或 workspace。
3. 首期建议固定 task→worker 亲和分派，同一任务在途最多一帧，避免跟踪前输入乱序和算法时序状态跨线程竞争。模型权重仍在 worker 间共享；分派变更需显式重建任务状态。
4. 同步 `process` 返回代表本次输入不再被 CPU/设备使用。不能把“已提交给 NPU”当作完成；不满足这一点的 SDK 适配不得接入这个参考合同。
5. 所有跨 ABI 函数在提供方捕获 C++ 异常，返回约定状态；不能用 `try/catch` 承诺恢复越界/崩溃。失败时输出清零/无所有权，成功返回的结果只有一次释放责任。
6. 模型/worker/结果由插件或其公共库/后端分配，并由实际分配者对应的销毁接口释放。插件可包装公共库句柄但不得直接释放其内部对象；runner 不跨库 `delete/free`，Go 更不能释放另一进程中的指针。
7. 关闭任务、释放结果、等待设备完成并 join worker 后，才能销毁模型组。正常操作不依赖 `dlclose` 作为热更新机制。

结果以平台中立的结构化感知数据输出，不把 RKNN 原始 tensor 指针传给 Go。建议封套包含包/版本、进程代次、任务/配置代次、流/帧 ID、时间戳有效性与 time base、源图尺寸、结果类型与 schema 版本。每种结果类型有自己的有界 payload 合同，不把所有感知结果强制缩减成检测框。

检测类样例应将框/点映射到原始输入图像坐标，明确格式、单位和范围，保留类别 ID 与分数；letterbox/裁剪变换由插件复原或显式描述。空结果是正常成功，错误不是“未检出”。只接受当前代次且可关联输入的结果；升级/重启后迟到结果丢弃并计数。最终具体类型布局随 SDK 头文件步骤冻结并加契约测试，不将示意字段当成现有协议。

## 5. IPC、帧分发和所有权

建议用私有 Unix `socketpair` 建立 Go↔runner 控制/结果通道及 Native broker↔runner 帧通道，经 exec 传递明确继承的 fd。避免在已初始化多线程/设备运行时后 fork 而不 exec。控制与数据的顺序不能跨通道臆定：模型就绪、任务注册确认后才允许 broker 投递对应代次的帧。

- 控制消息包含协议版本、长度/消息上限、请求 ID、包进程代次、操作及状态；区分请求已接收与动作已完成。
- fd 采用明确所有权转移或 dup；发送完成后关闭发送方不再需要的副本，接收方负责自己的 fd。创建时 CLOEXEC，只有明确传给 runner 的描述符被保留；Go 与 C++ 不重复关闭同一所有权。
- broker 的发送/等待不在 capture/decode 回调或队列锁内进行。每包/任务有界待处理队列和在途配额，AI 拥塞丢旧待处理帧，不能回收已被设备读取的在途帧。
- 不让多个算法包竞争 pop 同一个帧队列冒充广播；为订阅包扇出独立投递记录，共享底层不可变帧引用或已发布帧槽。

### 5.1 先建立可验证的帧传输

机制验证先用 Native 创建的有界共享内存帧槽，逐 plane 正确复制 CPU 解码帧，再释放原解码帧引用。这样 runner 的同步处理即使持有 IPC 帧到推理完成，也不会一直占用解码池。它是有拷贝的参考路径，不声称生产零拷贝已完成。

**现有接入缺口：** `native/src/nodes/decode/ffmpeg_decoder.cpp:113-126` 当前仅导出 `data[0]`、`linesize[0]` 等信息，未完整导出像素格式和所有 plane。不能据此假定 NV12 连续布局并直接复制 `width*height*3/2`。真实帧接入前需在 Native 内建立有明确 format、plane pointer/stride/长度、时间基准和来源的视图，引用寿命覆盖复制；不将厂商/FFmpeg 对象泄露进公共插件 SDK。无法证明布局时拒绝该格式，不读越界。

IPC 帧槽以帧 ID、slot ID、slot generation、进程/任务代次和有界 plane 描述传递。共享区偏移/长度必须溢出检查并落在映射范围内；`host_ptr`、`dev_ptr`、`shared_ptr` 不能跨进程直接解引用。

槽状态由 Native broker 单一拥有者管理：空闲 → 填充 → 发布只读 → 记录各接收者 lease → 全部安全归还后可复用。每个包每帧有独立 lease，不能凭一个 ACK 回收所有包仍使用的帧。重复/旧代次 ACK 不减少当前引用；发布后不得覆盖数据。协议明确各进程映射与通知的同步，不依赖跨进程 C++ `shared_ptr` 或任意可移植性未证明的共享原子对象布局。

### 5.2 生产硬件路径的门槛

DMA-BUF 作为后续硬件数据通路候选，通过 `SCM_RIGHTS` 传真实 fd，加 plane offset/stride/format 与必要同步信息；仅发送整数 fd 无效。MPP、RGA、RKNN 导入支持、模型 tensor layout、cache 同步和设备完成需要逐段证明；设备指针共享采用厂商明确的导出/导入机制，不能猜。

- 原始解码帧由 Native/解码后端分配与回收；runner 只借用/导入。
- 输入/输出 tensor 和预处理目标由对应 worker 的 RKNN/平台适配器管理，导入/映射/内存分别配对释放。
- 异步硬件尚在访问时不能归还帧。要提前释放原始帧以缓解解码池压力，应在硬件预处理完成、输入已转移到私有 tensor 后设计明确的 input-consumed 通知；这属于硬件适配步骤，不把当前同步参考接口误标为完成该优化。
- 进程退出后不能仅凭超时认为 DMA 完成。只有验证驱动清理/完成保证后才能回收相关 lease；无法确认时隔离受影响资源、停止投递并报告 `resource_blocked`，不盲目复用或重启。
- 共享内存参考路径若只是 CPU 读取，确认工作进程及其受控线程确实退出后可清理本代次 lease；不允许插件把借用输入逃逸给未受控后代进程。

## 6. Rockchip 模型与调度

参考设备为既有任务记录的 RK3568；SDK/Runtime、驱动、Toolkit2、量化类型和模型均未固定。Model Conversion Evidence Gate 当前为 `not-applicable`（架构/API 研究）；涉及输入归一化、量化后处理或真实 tensor 分配前必须补齐证据，不得沿用该状态跳过门禁。

- 为每个相同模型内容/设备/执行配置组建立根资源，验证 `rknn_dup_context(&root, &worker)` 候选。官方固定头文件同时含 `RKNN_FLAG_SHARE_WEIGHT_MEM`、`rknn_set_weight_mem`，但不自行拼接未验证的初始化顺序。
- 复制上下文的声明不保证权重共享；对比独立初始化和派生方案的正确性、主机 PSS/设备分配、`RKNN_QUERY_MEM_SIZE` 与销毁行为。不能把各 context 逻辑权重大小相加当作真实物理占用。
- 参考实现保守保持根资源到所有派生实例回收后；具体有效销毁次序按目标版本文档验证。
- 不支持共享时，明确报不支持/阻塞，不自动初始化 N 份权重完成验收。单实例可作为验证基线，但不能替代多实例共享目标。
- RK3568 单 NPU 执行资源，多个包的 context 仍竞争设备。以 CPU/预处理/后处理与推理重叠为优化方向，不默认增加线程就增加 NPU 并行度，也不启用 `ASYNC_MASK` 作为“多线程开关”。
- 多个模型各有根资源，不能共享不同内容的权重。只有 shape 相同不足以共享预处理 tensor，还必须一致的颜色、归一化、layout、量化和所有权合同；首期不引入跨包 tensor 缓存。

技术建议：调试与单元基线先用 1 个 worker，可受控设置为 2/4 进行对照；生产值在目标内存/时延测试后确定。单任务在途最多 1 帧、待处理最多 2 帧（丢旧），每包在途不超过 worker 数；同时设置每包/设备字节预算和输入任务数量上限，超额拒绝或降采样而非无限增长。实际字节预算依赖已测模型/帧大小，未填数前不得宣称生产容量已确定。

## 7. 状态机、升级与恢复

期望状态与实际状态分离。建议实际状态为 `stopped / starting / ready / draining / backoff / failed / resource_blocked`；版本切换是独立操作记录，不用一个状态掩盖期望停用。状态持久化/上报带版本、代次、失败阶段、重试计数、分析空窗与最近进展；底层错误经 Go 统一错误契约脱敏。

### 7.1 启动与正常停止

创建私有通道并 exec runner → runner 内装载插件/校验 ABI → 创建模型和 worker → 完成规定的模型/协议自检 → READY → 注册任务确认 → 允许 broker 投递。READY 不能仅表示进程存在；模型自检输入必须与转换合同一致，缺少证据时不能以全零任意输入假装通过真实模型验收。

主动停用设置期望停止；升级保留目标期望状态，但通过操作记录挂起普通自动恢复。两者都先撤销投递 → 唤醒等待/关闭队列 → worker 在所属线程等待设备在途结束、释放结果/任务状态及私有执行资源并退出 → join worker → 销毁共享模型资源 → runner 退出并由宿主回收。宿主退出先禁止重启调度，再排空子进程和 broker，最后关闭 Native engine 和数据库；不复用已返回的 Fx OnStart 临时 context 作为长期根 context。

停止期限到达不等于资源已释放。独立进程可在受控停止失败后终止，但真实硬件清理不确定时仍进入 `resource_blocked`，不能将进程 kill 的结果当作 DMA 回收凭证。

### 7.2 崩溃自动恢复

仅当期望为运行、无停止/升级操作、上一代进程确实退出且资源安全时重启当前版本。过期退出通知/重试定时器不能作用到新代次。

建议初始参数（本次审阅建议，不是已测 SLA）：退避 1s、2s、4s、8s、16s，连续失败预算最多 5 次自动重启；第 5 次重启仍未稳定则停止并报告。持续 READY 且有任务时确实取得处理进展满 5 分钟后才重置预算，空闲时以真实控制/健康响应判断存活，不因无帧误报卡死。生产参数在目标测试后调整；预算不因反复重建 runner 而清零，手动停用取消待执行重试。

初始化 ABI/模型不兼容、资源安全门失败等不可重试错误直接拒绝，不用重试掩盖。正常升级停止不计入崩溃预算；启动/停止的具体设备期限需要实际加载/清理数据，本设计不伪造固定 NPU 超时 SLA。

### 7.3 包级升级与受控回滚

1. 不覆盖运行中的目录。先静态校验 pending 包、资源/依赖完整性和配置兼容性，保存当前可用版本、配置及公共库依赖身份作为回退集合。
2. 记录升级意图与代次，停止该包投递，安全退出旧进程；宿主和其他包不重启。
3. 启动新版本并验证 READY。成功才提升 current 和成功配置/依赖记录；分析中断可观测，不补无限历史帧。
4. 新版本启动/就绪失败，清理并确认资源安全后，仅受控尝试一次 previous 及其兼容配置、匹配公共库。成功后标记“升级失败，已恢复旧版”，不把失败抹掉。
5. 无可用 previous/匹配依赖、配置不兼容、资源不安全或 previous 启动失败：保持 failed/resource_blocked 并报告；回滚启动阶段不再触发新旧循环或同版重试风暴。旧版成功进入运行后若将来独立崩溃，再按正常 R8 恢复。
6. 新版本已通过 READY 并投入运行后的普通崩溃按 R8 重启同版，不自动改变版本。

建议在现有 SQLite 中以版本化迁移记录包版本/配置、期望状态和 pending 操作；文件资源放外部数据目录。先完成不可变版本目录的写入与持久化，再事务记录安装/切换状态；SQLite 与文件操作不是单个原子事务。启动时按操作记录核对目录和哈希，清理/隔离未登记候选而不删除已确认可用版本。进程等待/SDK 调用不放数据库事务内。

## 8. 验证、迁移和残余风险

最小验证先做两个独立 C++17 示例插件与通用 runner，包含成功、错误、崩溃、慢处理和状态隔离场景；之后接入真实 Native 帧，再在匹配 SDK/模型/板端闭合 Rockchip。不是“CPU 桩通过即完成 R5/R6”。

- ABI：纯 C 编译、独立工程构建、版本/表大小/缺失符号拒绝；插件异常不越界、分配释放成对。
- 帧：多 plane/stride/偏移边界、时间基准、每包独立 lease、多订阅 ACK、旧代次结果/ACK、慢包背压和断流。
- 进程：包 A 崩溃/卡住、B 持续工作、主宿主存活；手动停用与退避竞态；预算耗尽；父进程退出后无失管 runner。
- 运维：升级成功、新版启动失败回退、无旧版、旧版失败、停止时硬件资源不安全、升级中宿主崩溃后的状态核对。
- 板端：1/2/4 worker 的正确性、主机/设备内存、吞吐/P95、队列等待、FD/内存稳定性和反复创建销毁，比较实际共享与非共享初始化。

现有 Engine 和媒体 API 不移除/改义；broker 管理通过新增纯 C 控制接口扩展，并回归已有 RTSP/包订阅/关闭合同。Native 静态库保留；runner 与 `.so` 单独构建，厂商依赖不进入主宿主。真实帧导出缺口只在接入步骤精准修复，不顺便改其他解码行为。

残余风险：厂商 Runtime/设备故障可影响其他包；全局 OOM 不被进程隔离自动解决；板端没有证据时不能确定权重共享、帧格式、容量和吞吐。主机协议测试与生产部署分开验收。完整执行顺序、门禁和回退点见 `implement.md`。
