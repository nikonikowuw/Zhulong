## 首轮交付选项与用户决策

1. 源码模块独立开发，最终与宿主一起编译：内部 C++ 接口/工厂即可，代价是新增算法仍需重新构建宿主。
2. 独立二进制插件，在约定目标平台兼容条件下不重编宿主即可安装：候选为版本化 C ABI、独立 SDK 与 `.so`；内部基类可选。若限可信插件且可接受停服务更新，可先不引入热卸载。
3. 独立进程算法服务：有利于崩溃隔离和运行时依赖分离；增加 IPC、共享内存/句柄传递、监控和部署成本。进程拆分本身也不等于安全沙箱。

用户在本任务讨论中已回复“B”，确认方向 2 的独立 `.so` 交付目标；随后回复“1”，确认首期仅接纳自己或受信任团队的插件，不开放未经审核的第三方原生插件。最新需求提出每算法包独立进程、进程内多个线程分别持有独立推理上下文，并以共享模型权重为目标。独立 `.so` 交付与独立 runner 进程可以结合，前述选项不是互斥的最终拓扑。版本化 C ABI 与可选内部基类仍是技术设计建议，具体合同待最终设计审阅；后续已确认的升级/恢复/回滚和平台决定见下方汇总与 `../prd.md`，不沿用首轮待决状态。

## 后续必须明确的安全与生命周期约束

- C++ 内部继承不是跨工具链的二进制兼容承诺；`extern "C"` 也不能消除架构、libc、厂商运行时等部署约束。
- 原始帧应由 Native 原有所有者分配/管理并负责回收。插件借用还是引用持有、何时归还，以及插件自有结果的释放方式均需明确，不能由 Go 或另一方猜测分配器并释放。
- 如有设备异步读取，不能仅因任务已提交就释放输入帧；必须有完成/引用与缓存同步契约。首期已确定 Rockchip，SDK、模型和量化类型仍未选定。
- 进程内 `.so` 不是故障或安全隔离边界，校验哈希/签名也不是沙箱。
- 停止新输入、排空在途调用/回调、释放实例与所有依赖插件代码的资源之前，不得卸载插件库。
