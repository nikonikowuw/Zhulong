# 一包一进程、多线程独立推理上下文：可行性与边界

状态：规划研究稿，不是已实现功能；未修改产品代码、未运行设备推理测试。产品决定以 `../prd.md` 为准，收敛后的技术建议与实施门禁见 `../design.md`、`../implement.md`。

## 1. 用户目标与结论

用户希望算法包独立运行在一个进程中，在该进程内通过多个线程、多个独立推理上下文执行推理，并共享模型权重资源。

- 进程/线程拓扑可实现，且与已选定的独立 `.so` 交付方式兼容：由一个通用原生 runner 可执行程序在各自工作进程中加载算法 `.so`。
- 模型文件只读取一次或 C++ 共享一个对象，不等于多个上下文真正共享设备侧权重。后者必须由厂商 SDK 的模型/执行分离或明确的共享/派生上下文机制支持并实测。
- 应将“每模型资源组共享不可变资源”与“每 worker 独占可变执行状态”分开；不能要求所有 SDK 用同一种厂商 context 句柄实现。

## 2. 仓库证据

- `native/src` 当前包含 ABI、capture/decode 与 pipeline，没有厂商推理适配后端或算法进程加载器。
- `native/src/pipeline/stream.hpp` 已有帧队列，`native/include/Zhulong/frame.hpp` 是包含 C++ 指针/回调的进程内帧对象，不是 IPC 格式。
- `.trellis/tasks/archive/2026-10/10-10-native-hardware-frame/prd.md` 列举 Rockchip、Ascend、NVIDIA 和 CPU 方向，但没有选定本任务首期 Runtime/SDK 版本。
- `.trellis/spec/native/directory-structure.md` 明确没有厂商专有 SDK；具体平台实现只是未来目录方向。
- 现有主宿主内的 Go/CGO 引擎接口与新增进程 IPC/进程内插件 C ABI 是三种不同的边界，不能混为一个 C++ 基类接口。

## 3. 候选拓扑

```text
Go 宿主
  ├─ 算法包进程管理：启动/退出检测/控制协议（恢复策略待定）
  └─ 现有 Native 采集解码 + 帧分发边界
          │ 有界帧传递；控制/结果采用 IPC
          ├─ runner：算法包 A
          │    ├─ 加载 A.so
          │    ├─ 共享模型资源组（同一模型与兼容执行配置）
          │    ├─ Worker 0：Execution 0 + 独立输入/输出/workspace
          │    ├─ Worker 1：Execution 1 + 独立输入/输出/workspace
          │    └─ Worker N：Execution N + 独立输入/输出/workspace
          └─ runner：算法包 B
               └─ 相同机制，独立地址空间和算法包故障边界
```

`.so` 不是可执行程序；不为每个算法复制一套进程管理程序。由通用 runner 装载包，宿主通过明确协议管理 runner。插件查询/初始化也应在工作进程中进行，不能先在宿主 `dlopen` 执行构造器再声称隔离。

新进程应经 exec 路径启动并在子进程内初始化推理 SDK，不把已初始化的多线程/设备运行时通过 fork 后不 exec 的方式继续使用。

## 4. 三层资源归属

| 层级 | 典型内容 | 共享规则与所有权 |
| --- | --- | --- |
| 模型资源组 | 权重、模型元信息、不可变标签/配置、可共享的编译资源 | runner 内由插件/后端适配器创建与释放；仅在 SDK 明确允许范围内供多个执行上下文使用 |
| 推理 worker | 独立执行上下文、输入/输出张量、激活/workspace、后处理临时区 | 每 worker 独占；同一上下文同一时刻只处理一项请求，异步任务完成之前不得复用其缓冲区 |
| 摄像机/分析任务 | 跟踪状态、规则状态、序号、时间戳与配置代次 | 按任务隔离；若有时序状态，不能随意在多个 worker 上并发读写或按乱序结果更新 |

线程不等于模型实例，也不等于摄像机任务。多路无状态推理可以分派到有界 worker 池；同一路有状态处理必须明确串行/亲和分派或结果重排策略。

概念接口可分为加载模型资源、创建执行实例、执行、销毁执行实例、卸载模型资源。它们是待设计职责而非已存在 API；C++ 基类可以只在进程内部使用，公开插件 ABI 保持 C 兼容。

## 5. 权重共享与并发不能凭拓扑保证

- 对同一模型调用 N 次完整加载接口，可能产生 N 份设备权重，即使模型文件或主机地址相同。
- `shared_ptr` 只帮助管理对象生存期，不提供 SDK 的线程安全，也不阻止 SDK 内部重复分配。
- SDK 若不能让独立执行实例共享权重，应明确报告此能力不满足；是否允许复制权重或退回单执行实例需用户决策，不能静默降级。
- 模型、设备、量化或执行配置不兼容时，不应强行共用同一个模型资源组；具体键与多版本/多设备策略待定。
- 设备可能串行调度多个 context；更多 CPU 线程可能增加排队和内存，而不增加吞吐。
- 若 SDK 上下文线程绑定，在所属 worker 内初始化/设置当前设备并销毁相关资源，遵循 SDK 文档，不假定模型加载线程可自由代替 worker 操作。

如果 SDK 真正共享权重，内存规划可用下式理解，但不作为实测承诺：

```text
总内存 ≈ 公共运行时开销 + 一份权重
        + N ×（执行上下文 + workspace/激活 + 输入输出）
        + 有界在途帧与结果
```

主机模型 mmap、主机 RAM 和设备内存分别计量。统一内存设备也可能有设备专用分配，不能只看进程 RSS 得出共享结论。

## 6. 主宿主与 runner 的帧传递

最小硬件无关验证路线可先使用有界共享内存帧槽，并允许从现有 CPU 解码帧复制一次；这能验证 IPC、崩溃边界和背压，但不等于生产零拷贝。

生产优化候选是 DMA-BUF 加 Unix Socket `SCM_RIGHTS` 传递真实 fd，前提是目标解码器、预处理器、运行时与驱动支持导入。不能只把 fd 数字作为普通整数发送，也不能发送主宿主的 `host_ptr`、`dev_ptr` 或 `shared_ptr` 供另一个进程直接解引用。设备指针跨进程共享需 SDK 专属导出/导入机制；不支持时需另外设计数据通路。

所有权约束：

- 原始帧由 Native 解码侧分配/管理并回收；runner 只持有明确租约或导入引用。
- 共享内存池若由帧分发方创建，分发方负责最终销毁；runner 释放映射/自己的 fd 引用，不能擅自覆盖未归还的帧槽。
- 元数据至少需表达格式、尺寸、各 plane stride/offset、长度、帧身份和代次；具体布局/时间基准待设计。现有 HardwareFrame 的字段不能自动覆盖所有多平面格式与 IPC 需要。
- 设备完成同步与 CPU cache 同步分别处理；输入只是提交给硬件时不能返还上游复用。
- 工作进程异常退出后，由宿主处理其在途租约；若设备仍在访问，不能仅凭超时或进程消失就把原始缓冲区重新发给生产者。必须验证驱动清理/设备完成保证，必要时隔离资源并触发受控恢复。
- 多个算法包需要各自有界投递/消费状态；不能让多个包竞争 pop 同一个帧队列却误以为实现同帧广播。

## 7. 生命周期与故障边界

正常退出建议顺序：停止接收新请求 → 唤醒阻塞 worker → worker 等待在途设备任务结束并在所属线程销毁独立执行上下文/私有缓冲后退出 → join 所有 worker → 卸载模型共享资源 → 退出 runner。用户已确认采用包级重启更新，不以存活进程内热 `dlclose` 为首期目标；停止超时和异常恢复细节仍需后续设计。

任一 worker 原生崩溃可能终止整个算法包进程，该包所有任务都会受影响。进程隔离用于避免插件的普通地址空间故障直接终止宿主或其他包；不隔离共享设备/驱动故障，也不自动解决宿主的 IPC 实现错误、全局 OOM 或无界资源消耗。包级资源上限、超时和恢复需要设计，不能把“单独进程”当作充分可靠性保障。

## 8. 验证路径（尚未执行）

1. 先指定芯片、SDK/Runtime/驱动版本与模型/量化配置，核对官方的共享权重和多上下文并发合同。
2. 对同一个模型固定输入/预处理与测试负载，对比 1、2、4 个 worker 的加载耗时、主机/设备内存、吞吐、P50/P95 延迟与正确性；线程数只是测试点，不是批准的默认配置。
3. 区分共享一份模型资源并派生执行实例与 N 次完整加载，对比设备侧内存增长；CPU 桩或 RSS 不能证明真实 NPU 权重共享。
4. 测试慢包、多包同帧、乱序结果、输入断流、正常停止与进程崩溃，验证队列有界、宿主不被阻塞、其他包可继续处理、原始帧不提前复用。
5. 用 Linux procps `ps -eLo pid,tid,nlwp,psr,comm` 观察进程/线程拓扑；设备内存与执行并发以 SDK/驱动观测为准。

## 9. 已确认的算法包职责

用户选择 A（感知算法包）：

- 插件负责模型相关前处理、一个或多个模型的执行与后处理，向公共层输出结构化感知结果。
- 通用跟踪、区域/越线等业务规则和事件管理属于公共能力，不由每个感知插件重复实现；算法自身必需的时序状态仍可保留在包内，并按任务隔离。
- 通用 runner 承担装载、通信与 worker 调度等运行机制，不把算法-specific 后处理塞进 runner 核心。插件不直接进行告警落库或外部业务通知。
- 公共层是职责边界，不等于所有计算都必须放在 Go；高频跟踪/规则计算的具体落点在后续设计中结合现有 Native/Go 边界决定。
- 结果契约应能关联输入、区分版本/代次并解释坐标空间；具体字段与首期结果类型尚未定稿。不能把感知分类标签或分数直接当作已判定的业务告警。

以上仅定义接口与依赖边界，不把实现完整跟踪/规则/事件系统纳入本次架构任务。

## 10. 已确认升级、崩溃恢复与回滚策略

用户已确认首期 Rockchip；既有媒体接入 PRD 记录参考设备为 RK3568，Runtime/SDK 和板端数据仍未知。版本/模型数据作为后端实现验收前置条件继续记录，公共接口保持后端中立，不同时承诺所有平台共享行为。

用户选择升级方案 1（包级重启）：

- 只重启该包工作进程，宿主和其他包不重启；停旧、排空并释放依赖资源后启动新包，减少同一设备上新旧模型同时驻留的峰值内存。
- 允许该包分析短暂中断，不保证中断期间每帧都有分析结果，也不通过无界缓存掩盖中断。
- 首期不做新旧进程并存的无感切换，也不做存活进程内的插件热卸载。进程代次与结果归属仍须校验，避免已过期结果影响当前状态。
- 正常升级的排空/释放必须等待设备不再访问资源；遇到停止超时或驱动异常时，不能强行复用仍可能在途的硬件缓冲区。

用户选择崩溃恢复方案 1（有界自动恢复）：

- 宿主观察工作进程退出，对仍应运行的包按退避和次数/时间窗口上限尝试重新拉起；连续失败达到上限后停止重试并暴露故障，避免重启风暴。
- 管理员主动停用、宿主退出与正常升级停止不作为意外崩溃计数，不能因自动恢复覆盖新的停用意图。设计需处理退避期间被停用的竞态。
- 资源回收安全门优先于自动重试。不能因为工作进程已退出或超时，就假定设备不再访问缓冲区；无法证明安全时应停在可诊断的失败/阻塞状态。
- 具体退避与预算参数、成功运行后何时重置预算、就绪判定及任务/租约代次处理，在技术设计中提出并纳入最终审阅。本轮不擅自指定具体数值为已确认需求。

用户选择回滚方案 1：在新版本启动/就绪检查失败时，清理失败进程后受控尝试恢复上一可用版本；前提是旧版本及其兼容配置仍可用且设备资源状态安全。旧版本也启动失败时停止并报告，不在新旧版本间无限切换。新版本已正常运行后的任意故障不自动等同于触发此回滚。

自动重启同一版本和升级失败自动切换版本是两个不同的行为，用户现已分别批准。任何方案均不承诺自动修复驱动或设备级故障。架构已进入最终文档审阅，技术建议与分阶段门禁见 `../design.md`、`../implement.md`；没有启动实现。
