# feat(core): unify entity primary key generation with ULID

## Goal

Unify dynamic entity primary key generation using clean, monotonic ULIDs across backend services (`person`, `camera`, `algorithm/task`), replacing ad-hoc random strings (`crypto/rand.Text()`), table-scanning numeric string increments (`GetNextNumericID`), and bloated pseudo-semantic composite strings (`task_{cam}_{algo}`).

## Background & Rationale

- SQLite tables `persons`, `person_faces`, `cameras`, and `analysis_tasks` all define `id TEXT PRIMARY KEY NOT NULL`.
- Currently:
  - `internal/person` uses `crypto/rand.Text()`: 26-char Base32 random string, collision-resistant but lacks temporal monotonicity, resulting in random B-Tree insertions and lack of chronological sortability.
  - `internal/camera` uses `GetNextNumericID()` when `req.ID` is empty: queries `SELECT COALESCE(MAX(CAST(id AS INTEGER)), 0) + 1 FROM cameras WHERE ...` under an in-memory Go mutex (`createMu`). This incurs lock contention, database table scan, and lexicographical sort anomalies (`"10"` < `"2"`).
  - `internal/algorithm` defaults `task.ID` to `"task_" + CameraID + "_" + AlgorithmID`: when `CameraID` becomes a 26-character random ULID, composite IDs become unwieldy (>40 chars) without human readability, coupling surrogate primary keys with foreign business state.
- **Decision**: All dynamic surrogate primary keys generated by the system will be **pure ULIDs (26-character Crockford's Base32)**. Human readability belongs to entity names/labels and relational queries, while primary keys remain clean, opaque, temporally ordered surrogate identifiers.

## Requirements

1. **Unified ID Utility (`internal/idutil`)**:
   - Introduce `github.com/oklog/ulid/v2`.
   - Implement thread-safe, cryptographically secure monotonic ULID generator (`idutil.New() string`).
   - Provide auxiliary functions: `idutil.IsValid(string) bool`, `idutil.Time(string) (time.Time, error)`.
   - Maintain zero heap allocation where possible on the hot path.
2. **Personnel & Face Gallery Domain (`internal/person`)**:
   - Replace `newID()` in `internal/person/service.go` with `idutil.New()`.
   - `persons.id` (internal surrogate key) and `person_faces.id` (internal surrogate key) use ULID.
   - `persons.person_id` is the external business key (optional / nullable `*string`); it remains completely decoupled and is NOT populated by ULID when empty.
   - Maintain `{owner_row_id}_{face_id}.ext` file naming contract seamlessly (since ULID matches the 26-character Base32 format of `rand.Text()`).
3. **Camera Domain (`internal/camera`)**:
   - When creating a camera without a client-provided `id`, assign `idutil.New()` directly.
   - Remove `GetNextNumericID` from `Store` interface, `gormCameraStore`, and `service.go`.
   - Remove `createMu` mutex in `camera.Service` used solely for ID allocation.
   - Preserve client-specified custom `req.ID` support for backward compatibility.
4. **Analysis Task Domain (`internal/algorithm`)**:
   - When creating an analysis task without a client-provided `id`, assign `idutil.New()` directly instead of composite string concatenation.
   - Preserve client-specified custom task `req.ID` support for testing and manual overrides.
5. **No Breaking DDL Changes**:
   - Keep existing SQLite schema (`TEXT PRIMARY KEY`) as-is. Existing data remains valid.
6. **Specifications & Guidelines**:
   - Update `.trellis/spec/backend/database-guidelines.md` to establish ULID as the repository-wide standard surrogate key strategy for all `TEXT PRIMARY KEY` entities.

- [x] `internal/camera`: creates cameras with valid 26-char ULIDs when omitted; `GetNextNumericID` and `createMu` removed.
- [x] `internal/algorithm`: creates analysis tasks with valid 26-char ULIDs when omitted.
- [x] All tests in `internal/camera`, `internal/person`, and `internal/algorithm` updated and passing with `-race`.
- [x] `.trellis/spec/backend/database-guidelines.md` updated with the new ULID standard.

## Out of Scope

- Modifying `users` or `audit_logs` SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` tables (these remain native SQLite sequential integers).
- Historical data migration (existing database records with numeric or custom string IDs remain valid and supported).
- Removing the user's ability to specify a custom `id` in requests (custom IDs remain optional for client overrides).
